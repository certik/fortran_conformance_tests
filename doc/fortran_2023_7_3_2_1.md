## Evidence boundary

R702/R703 programs are **positive admission controls**, not proof of every
interaction of types, attributes, ranks, parameters, or procedure contexts.
Constraint negatives are external `diagnose` fixtures: a genuine error at
the declared source point can satisfy the reporting contract without
compulsory fatal rejection. Semantic predicates prevent a generic
unsupported TYPEOF/CLASSOF parser message from silently becoming semantic
corroboration. No nonfatal warning policy is invented.

Message predicates qualify this finite evidence; the standard does not
mandate those words. A differently worded, properly located report needs
independent adjudication rather than being silently ignored or equated
with an unsupported-keyword parse error. Missing reports describe the
declared compiler configuration, not every possible processor option.

The negative C707 character declaration has no `::`; otherwise C730 would
mask the owned trailing-comma condition. Its original printed `(R702)`
association is retained, even though the wording explicitly names the
TYPE wrapper. C703 does not ban an abstract `CLASS IS` guard. C705 does not
add an extensibility condition to CLASSOF. C708 negatives have no secondary
ALLOCATE/ALLOCATED misuse. C713's OPTIONAL attribute belongs to the operand,
and its repaired controls remove OPTIONAL rather than changing the
assumed/deferred oracle.

The effect programs use initialized finite values and supported KIND
inquiries, explicit internal interfaces, and allocation/association guards.
A character dummy probe distinguishes an assumed operand's value from a
new assumed parameter by preserving a longer actual argument's trailing
sentinels. Deferred-parameter probes allocate copies at lengths different
from the operand. Declared-type probes use concrete sibling extensions,
and unlimited CLASSOF does not freeze the operand's dynamic type.

The C710 **parameter-only ordering diagnostic remains pending**: the
prior-type/parameter controls and forward-type negatives do not supply an
independent missing-parameter-order witness. Other finite boundaries and
unsupported/source-only candidates are recorded with complete compiler
observations in the author handoff; no draft result is fixture approval.
In particular, named enums/enumerations, CLASSOF of nonextensible types,
TYPEOF/CLASSOF, and polymorphic PDTs must not be rewritten merely to satisfy
a reference compiler. No whole-standard completion or processor-interface
adherence is claimed.

Dependency ownership stays with 7.2, 7.3.2.2-7.3.3, 7.4-7.6,
8.2/8.7, 9.4.5/9.7.1, 11.1.11, and the relevant Clause 15 rules.
The original pages and precise diagnostic basis are recorded per requirement.
The finite FUNCTION-prefix negatives do not exhaust every excluded R703
context (for example IMPLICIT and procedure interface specifications).

### R702: Type-spec admits four type categories

**Source:** 7.3.2.1 R702; J3/24-007 PDF 77, printed 63, lines 15-18. **Class:** Syntax.

**Definition:** A type-spec is an intrinsic, derived, enum, or enumeration type specifier. The last two
are distinct nonintrinsic types, not derived types. The union preserves the defining
syntax, parameter conditions, and contextual restrictions of each alternative.

**Diagnostic obligation:** required.

**Facets:** `intrinsic`, `derived`, `enum`, `enumeration`.

**Oracle:** Four independent positive controls use an explicit type-spec in a small array
constructor and check two initialized elements. Named enum values are constructed as
enum values, not arbitrary integers without the required enumerator relationship.

**Oracle limitation:** Admission of each alternative is not proof of every type interaction or every enclosing
context. No malformed defining alternative is misattributed to the union as an isolated
R702 negative. Named enum/enumeration controls remain valid-source drafts if reference
implementations lack them.

**Dependencies:** 7.4.1/R704-R706 (PDF 80), 7.5.9/R754-R755 (PDF 106), 7.6.1/R764 and 7.6.2/R770 (PDF
109-112), 7.8/R777-R778/C7121-C7125/p3 (PDF 114-115). 4.1.2 and 4.2 p2(3) (PDF 45-46)
supplies the numbered-syntax reporting basis, not mandatory fatal rejection.

### R703: Declaration-type-spec has ten alternatives

**Source:** 7.3.2.1 R703; PDF 77, printed 63, lines 20-29. **Class:** Syntax.

**Definition:** The declaration category admits a bare intrinsic specifier; TYPE around an intrinsic,
derived, enum, or enumeration specifier; CLASS around a derived specifier; CLASS(*);
TYPE(*); and TYPEOF or CLASSOF applied to a data-ref. TYPE(*) is assumed-type; CLASS(*)
is unlimited polymorphic. TYPEOF/CLASSOF do not accept an arbitrary expression merely
because it has a type.

**Diagnostic obligation:** required.

**Facets:** `intrinsic`, `type-intrinsic`, `type-derived`, `type-enum`, `type-enumeration`, `class-derived`, `class-unlimited`, `type-assumed`, `typeof`, `classof`.

**Oracle:** Ten separately compiled admission controls exercise the ten alternatives. The
assumed-type object is a scalar INTENT(IN) dummy in an internal procedure and is used
only by PRESENT; polymorphic objects have suitable attributes and are allocated or
associated before value access.

**Oracle limitation:** These are positive controls for the union. They do not prove all type identity, dynamic
type, parameter propagation, interoperability, or argument association effects. In
particular the TYPE(*) control does not inspect its value or claim a C ABI result.
TYPEOF/CLASSOF semantic evidence is separately owned by S7.3.2.1-001.

**Dependencies:** 8.2/R801 (PDF 117); 7.3.2.2 p2-p3/C714-C716 (PDF 78), 7.3.2.3 and 7.3.3 (PDF 79); local
C704-C713; defining type alternatives in 7.4-7.6. 15.4.2.1-15.4.2.2 (PDF 325) supplies
explicit internal interfaces. Numbered syntax has the 4.2 p2(3) reporting basis.

### C703: R702 derived type-spec cannot be abstract

**Source:** 7.3.2.1 C703 (R702); PDF 77, printed 63, line 19. **Class:** Restriction.

**Definition:** A derived-type-spec used as the derived alternative of R702 cannot name an abstract
type. The association with R702 is part of the premise. It does not prohibit
CLASS(abstract-type) declarations or a CLASS IS(abstract-type) guard, whose
derived-type-spec does not pass through R702.

**Diagnostic obligation:** required.

**Facets:** `concrete-type-spec`, `abstract-type-spec`, `class-is-boundary`.

**Oracle:** A located compile-report fixture allocates an abstract type through a properly declared
polymorphic allocatable. Its minimally repaired control substitutes a concrete extension
in the allocation. A separate initialized CLASS IS guard control shows the R1156
boundary without calling it an abstract TYPE IS case.

**Oracle limitation:** No abstract constructor is used: that would add an independent violation. The allocation
has an explicit compatible type-spec, scalar object, and correct attribute. A report
must be at the allocation, not at a type definition or recovery summary. Required means
detection/reporting capability under 4.2 p2(3), not a compulsory fatal exit.

**Dependencies:** 7.5.7.1 p1/p4 (PDF 104); 9.7.1.1/R929/C936-C940 (PDF 160); 11.1.11.1/R1156/C1164-C1167
and 11.1.11.2 (PDF 225-226); 4.1.2 p2 and 4.2 p2(3) (PDF 45-46).

### C704: Ordinary declaration parameter values are specification expressions

**Source:** 7.3.2.1 C704 (R703); PDF 77, printed 63, lines 30-31. **Class:** Restriction.

**Definition:** In a declaration-type-spec, each type-param-value other than colon or asterisk must be a
specification expression. This applies to positional and named parameters, intrinsic and
derived. Specification expressions are not universally constant expressions: the context
and restricted-expression rules matter. The colon and asterisk exceptions here do not
waive their separate attribute and context restrictions.

**Diagnostic obligation:** required.

**Facets:** `constant-values`, `dummy-specification-length`, `deferred-colon`, `assumed-asterisk`, `named-derived-parameters`, `nonspecification-length`.

**Oracle:** Controls use supported KIND inquiries, a nonoptional INTENT(IN) scalar length dummy,
legal assumed/deferred character contexts, and a PDT with named kind/length parameters.
The isolated negative changes that length dummy to OPTIONAL; removing OPTIONAL is the
repair. The diagnostic is bound to the character declaration.

**Oracle limitation:** The negative uses a scalar integer length, not a nonconstant kind (which would
independently violate C701/R706) or an unsupported kind. The optional dummy's value is
excluded by the restricted-expression definition regardless of runtime presence. No
diagnostic requirement is inferred from arbitrary prose: the owned numbered C704 invokes
the specification-expression definition.

**Dependencies:** 7.2/R701-C702 (PDF 76); 10.1.11 p1-p4/R1029/C1011, especially p2(2) (PDF 185-186);
7.4.4.2/R721-R723/C726 (PDF 84-85); 7.5.3 and 7.5.9 (PDF 91-93,106). 4.1.2/4.2 gives
required reporting rather than required refusal to compile.

### C705: CLASS named derived types must be extensible

**Source:** 7.3.2.1 C705 (R703); PDF 77, printed 63, lines 32-33. **Class:** Restriction.

**Definition:** When a declaration-type-spec uses CLASS with a derived-type-spec, that type must be
extensible. Under 7.5.7.1, SEQUENCE and BIND types and the intrinsic-module types C_PTR
and C_FUNPTR are excluded. An abstract derived type can be extensible and is not banned
by this condition. The text names the CLASS keyword, not CLASSOF.

**Diagnostic obligation:** required.

**Facets:** `extensible`, `abstract-extensible`, `sequence-excluded`, `bind-c-excluded`, `c-ptr-excluded`, `c-funptr-excluded`, `nonclass-intrinsic-module-types`.

**Oracle:** Four independent located negatives use SEQUENCE, BIND(C), C_PTR, and C_FUNPTR with
otherwise eligible POINTER declarations. Repairs remove SEQUENCE/BIND(C) or replace
CLASS by TYPE for the intrinsic-module types. An abstract-extensible control allocates a
concrete extension and checks initialized data.

**Oracle limitation:** No kind representation is hard-coded: BIND(C) uses C_INT. Pointer controls begin
disassociated; no undefined pointer value or abstract dynamic object is read. These
exclusions are a finite test of the exact extensibility definition, not an inherited ban
on every CLASSOF operand. Diagnostics must identify the declaration, not an unsupported
USE or type definition.

**Dependencies:** 7.5.7.1 p1/p4 (PDF 104), 7.3.2.3/7.3.3 (PDF 79), 18.2 ISO_C_BINDING types/constants, and
4.1.2/4.2 p2(3). C708 supplies the independently satisfied POINTER/ALLOCATABLE premise.

### C706: TYPE with a derived specifier cannot name an abstract type

**Definition:** TYPE(derived-type-spec) cannot specify an abstract type. This is a declaration
restriction, distinct from the R702 type-spec restriction C703 and the TYPEOF operand
restriction C711. Adding POINTER or ALLOCATABLE does not exempt this TYPE form; using
CLASS is a different form with its own conditions.

**Diagnostic obligation:** required.

**Facets:** `concrete-type`, `abstract-type`.

**Oracle:** The negative declares a TYPE object of a previously defined abstract type. The repaired
control removes only ABSTRACT from the type definition, initializes a small component,
and checks it. Report the object declaration, not the ABSTRACT type definition.

**Oracle limitation:** No deferred type-bound procedure, missing binding, constructor, or invalid type ordering
is involved. The control is admission of the repaired TYPE declaration, not evidence
that abstract CLASS entities are forbidden. The reporting contract does not require
fatal rejection.

**Dependencies:** 7.5.7.1 p4 (PDF 104); 7.3.2.2 p2 (PDF 78); 8.2/R801 (PDF 117); 4.1.2 and 4.2 p2(3) (PDF

### C707: TYPE-wrapped intrinsic specifiers cannot end in a comma

**Source:** 7.3.2.1 C707, printed association (R702); PDF 77, printed 63, line 35. **Class:** Restriction.

**Definition:** In the explicitly named TYPE(intrinsic-type-spec) form, the inner intrinsic-type-spec
must not end with a comma. Preserve the draft's printed R702 association without
silently changing the official rule identity or ignoring its explicit TYPE-wrapper
wording.

**Diagnostic obligation:** required.

**Facets:** `wrapped-no-comma`, `unwrapped-comma`, `wrapped-comma`.

**Oracle:** The negative uses TYPE(CHARACTER*3,) word, without a double-colon separator. Deleting
the inner comma is the minimal repair. A separately compiled program with an unwrapped

repaired TYPE control.

**Oracle limitation:** A trailing comma after INTEGER or inside KIND selectors would invent a separate syntax
defect. A double colon would independently violate C730, so neither negative nor repair
has one. The diagnostic point is the wrapped declaration; there is no required fatal
status.

**Dependencies:** 7.4.4.2/R721-R723 and C729-C730 (PDF 84-85); 8.2/R801 (PDF 117); 4.1.2 and 4.2 p2(3).

### C708: CLASS and CLASSOF entities need one eligibility condition

**Source:** 7.3.2.1 C708; PDF 77, printed 63, lines 36-37. **Class:** Restriction.

**Definition:** An entity declared using CLASS or CLASSOF must be a dummy argument or have ALLOCATABLE
or POINTER. These are alternatives, not cumulative requirements. A function result is
not a dummy argument merely because it belongs to a procedure; it needs the appropriate
attribute. The operand of CLASSOF does not confer attributes on the new entity.

**Diagnostic obligation:** required.

**Facets:** `class-dummy`, `class-allocatable`, `class-pointer`, `classof-dummy`, `classof-allocatable`, `classof-pointer`, `class-ineligible`, `classof-ineligible`.

**Oracle:** Separate CLASS and CLASSOF controls exercise dummy, allocated allocatable, and
associated pointer forms with an explicit internal interface. Two declaration-only
negative programs have an ordinary nondummy local without either attribute; the minimal
repair adds ALLOCATABLE and never reads the unallocated object.

**Oracle limitation:** The bare-local negatives do not add ALLOCATE or ALLOCATED calls that would independently
require the missing attribute. The repaired empty programs are positive admission
evidence, not runtime type effects. Required reporting is from the numbered constraint
under 4.2, not a fatal-exit policy.

**Dependencies:** 7.3.2.3, 8.5 attributes, 15.4.2.1-15.4.2.2 (PDF 325), and 15.6.2.2 p3 (PDF 354). C705,
C709-C713 are independently satisfied in each relevant control or negative.

### C709: TYPEOF and CLASSOF have two allowed statement locations

**Definition:** A TYPEOF or CLASSOF specifier may occur only in a type declaration statement or a

every context accepting declaration-type-spec, such as a FUNCTION prefix, IMPLICIT
mapping, or procedure interface specification.

**Diagnostic obligation:** required.

**Facets:** `typeof-declaration`, `classof-declaration`, `typeof-component`, `classof-component`, `typeof-function-prefix`, `classof-function-prefix`.

**Oracle:** Controls place each keyword in a function-result type declaration and in component

**Oracle limitation:** ALLOCATE(TYPEOF(...)) and TYPE IS(TYPEOF(...)) would instead misuse R702; they are not

the semantic restriction; retain the repaired control outcome and complete diagnostic.

**Dependencies:** 8.2/R801 (PDF 117), 7.5.4.1/R737/C749/C759 (PDF 93), 15.6.2.1/R1529-R1530 (PDF 352),

### C710: TYPEOF and CLASSOF require established type information

**Source:** 7.3.2.1 C710; PDF 77, printed 63, lines 40-41. **Class:** Restriction.

**Definition:** The data-ref operand of TYPEOF or CLASSOF must have both its type and its type
parameters previously declared or established by the applicable implicit typing rules. A
subsequent declaration under IMPLICIT NONE is not equivalent to prior establishment.

**Diagnostic obligation:** required.

**Facets:** `typeof-prior-type-parameters`, `classof-prior-type-parameters`, `typeof-implicit`, `classof-implicit`, `typeof-forward-reference`, `classof-forward-reference`, `parameter-only-ordering`.

**Oracle limitation:** This does not read an uninitialized value: the type information is established before
any effect probe. Implicit CLASSOF uses a host-defined extensible derived type, not the

pending, not inferred from admission or from an unrelated later redeclaration error.

### C711: TYPEOF excludes unlimited polymorphic and abstract operands

**Source:** 7.3.2.1 C711; PDF 78, printed 64, line 1. **Class:** Restriction.

**Definition:** The data-ref in TYPEOF cannot be unlimited polymorphic or of abstract declared type. A
concrete dynamic allocation does not supply a permitted substitute for the declared
type. Assumed-type entities are also unlimited polymorphic under 7.3.2.2 p3. The
restriction is on TYPEOF, not on CLASSOF.

**Diagnostic obligation:** required.

**Facets:** `concrete-declared-type`, `unlimited-polymorphic`, `abstract-declared-type`.

**Oracle:** Separate negatives apply TYPEOF to a previously declared CLASS(*) allocatable and to a
CLASS(abstract-root) allocatable. Minimal declaration-only controls use
CLASS(concrete-root) or remove ABSTRACT. Each report must identify TYPEOF, not the legal
polymorphic operand declaration.

**Oracle limitation:** No value, deferred parameter, or allocation status is read by these declaration-only
isolates. S7.3.2.1-001 separately distinguishes declared from dynamic type. No
additional negative is attributed to C711 for an unrelated inaccessible or undefined
type. A mere unsupported TYPEOF parser failure is not semantic corroboration.

**Dependencies:** 7.3.2.2 p3 (PDF 78), 7.3.2.3 p3-p5 (PDF 79), 7.5.7.1 p4 (PDF 104), and 4.1.2/4.2 p2(3).

### C713: Optional TYPEOF and CLASSOF operands need nonassumed nondeferred parameters

**Source:** 7.3.2.1 C713; PDF 78, printed 64, lines 3-4. **Class:** Restriction.

**Definition:** If the TYPEOF or CLASSOF data-ref has OPTIONAL, none of its type parameters may be
deferred or assumed. The condition is on the operand, not on the newly declared entity.
Presence at runtime does not waive this static restriction. Fixed parameters on an
OPTIONAL operand and assumed/deferred parameters on a nonoptional operand do not violate
this constraint.

**Diagnostic obligation:** required.

**Facets:** `typeof-optional-fixed`, `classof-optional-fixed`, `typeof-optional-assumed`, `typeof-optional-deferred`, `classof-optional-assumed`, `classof-optional-deferred`, `nonoptional-assumed`, `nonoptional-deferred`.

**Oracle:** Four isolated negatives cross the two keywords only with the two forbidden parameter
categories: character for TYPEOF, a one-length PDT for CLASSOF. Each minimally repaired
control removes OPTIONAL. Two additional fixed-parameter optional controls execute with
the operand both present and absent, guarding any actual value reference with PRESENT.

**Oracle limitation:** The deferred declarations carry ALLOCATABLE and assumed parameters occur only on proper
dummies. No intrinsic operand is passed to CLASSOF; all PDTs are defined before use.
Declaration-only repaired controls are admission evidence, not a claim about parameter
values. The reporting point is the TYPEOF/CLASSOF declaration and its message must
concern OPTIONAL.

**Dependencies:** 7.2/C702/p5-p7 (PDF 76), 7.4.4.2/C726 (PDF 84-85), 7.5.9/C7100 (PDF 106), 15.4.2.2 (PDF

### S7.3.2.1-001: TYPEOF and CLASSOF preserve declared type and parameter semantics

**Source:** 7.3.2.1 p3; PDF 78, printed 64, lines 8-12. Note 2 explains, but does not separately mandate, the assumed-parameter distinction. **Class:** Effect.

**Definition:** For a data-ref that is not unlimited polymorphic, TYPEOF and CLASSOF specify its
declared type and corresponding type parameter values, not its current dynamic type. The
exception is that a parameter deferred in data-ref remains deferred. TYPEOF declares a
nonpolymorphic entity and CLASSOF a polymorphic entity. CLASSOF of a CLASS(*) data-ref
is equivalent to CLASS(*). Assumed parameters supply their values rather than making the
new entity assumed, including when that entity is itself a dummy argument.

**Diagnostic obligation:** not-required.

**Facets:** `typeof-declared-nonpolymorphic`, `classof-declared-polymorphic`, `typeof-intrinsic-kind-length`, `typeof-assumed-value`, `classof-assumed-value`, `classof-derived-kind`, `typeof-deferred`, `classof-deferred`, `classof-unlimited`, `component-array-data-ref`.

**Oracle:** Independent runtime programs distinguish a declared root from a dynamic extension; test
a polymorphic result's ability to allocate sibling extensions; compare supported
intrinsic kinds and explicit lengths; use a character dummy with a longer actual and
untouched trailing sentinels to distinguish copied values from a copied asterisk; check
named PDT kind/assumed-length values; allocate deferred character/PDT copies with
lengths different from the source; and allocate a CLASSOF(CLASS(*)) result to types
unrelated to its operand's current dynamic type. A component/array data-ref control
checks type/parameters without inheriting rank.

**Oracle limitation:** This is finite effect evidence, not every combination of type category, kind, rank,
component path, pointer association, or optional attribute. All allocations/associations
and sizes are checked before value or deferred-parameter access. Zero-sized arrays,
coarrays, processor source interfaces, C ABI representation, and full enum
TYPEOF/CLASSOF runtime interactions are outside this finite plan. Unsupported F2023
syntax, PDT lowering failures, crashes, and reference F2018 mode do not invalidate a
source-valid oracle and do not count as effects. No negative or fatal diagnostic is
inferred from this prose paragraph.

**Dependencies:** 7.3.2.2-7.3.3 (PDF 78-79); 7.2 (PDF 76); 7.4.4.2 (PDF 84-85); 7.5.3/7.5.9 (PDF
91-93,106); 9.4.5 p2 (PDF 153); 9.7.1.1 (PDF 160-161); 11.1.11 (PDF 224-226); 15.4.2.2
(PDF 325); 15.5.2.5 p3-p5 (PDF 340) permits a scalar default-character actual longer
than its fixed-length dummy. 16.9.118/KIND (PDF 424) supplies portable kind inquiries,
and 16.9.171/RANK (PDF 449) checks the scalar receiving declaration. The execution
interpretation is required by 4.2 p2(1), not an extra reporting obligation.
