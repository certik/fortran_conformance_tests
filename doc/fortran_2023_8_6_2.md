## Exact finite grammar

R832 has an optional double colon but a required declaration list.
The list is nonempty and comma-separated through assumed R401. Both
`ALLOCATABLE name` and `ALLOCATABLE :: name` are admitted in complete
eligible declaration contexts. A listless statement is not a SAVE-like
specification of every object in a scope.

R833 has an object name followed by two independently optional groups:
the parenthesized array specification, then the bracketed coarray
specification. The bounded positive matrix is:

| Form | Required interpretation and qualifications |
| --- | --- |
| bare object name | No new array/coarray specification here; it can be an ordinary scalar or retain specifications supplied elsewhere. |
| `name(:)` / `name(:,:)` | Deferred array specification with small rank; not actual allocated bounds. |
| `name[:]` | Scalar allocatable coarray with deferred coshape; no array parentheses are required. |
| `name(:,:)[:]` | Array specification precedes coarray specification; rank and corank remain distinct and satisfy the standard ceiling. |
| prior `REAL B(:)` then bare `B` | The statement supplies ALLOCATABLE without repeating the prior array specification. |
| prior deferred CODIMENSION then bare name | Corank/coshape is supplied through its own canonical declaration route, without another explicit specification. |
| prior valid RANK clause then bare name | RANK and C834 retain ownership; this packet neither copies the frozen RANK catalogue nor infers an allocation. |

The generic `array-spec` and `coarray-spec` productions are not permission
to ignore C834 or C827. An ordinary allocatable array needs the permitted
rank-clause/deferred-shape route, and an allocatable coarray needs deferred
coshape. Explicit bounds, assumed shape, assumed size and assumed rank
have distinct conditions and owners. Assumed-rank requires its proper
dummy/associate context; it is not a generic local-array repair.
An allocatable assumed-rank dummy can use `name(..)` in a complete valid
declaration, subject to C839/C840 and its real interface. It is not to be
rejected by treating every assumed-rank entity as an ordinary
deferred-shape array, nor combined with a forbidden CODIMENSION/VALUE.

Parentheses here are **array declarations**, not element references or
actual type parameters. A CHARACTER length or PDT parameter belongs to
the corresponding type specification. The first separation control uses
constant CHARACTER length three with scalar/array object forms; a deferred
type-parameter example needs its full canonical premises rather than an
extra already-specified ALLOCATABLE attribute.
Deferred shape and deferred coshape are not deferred type parameters.
In particular, an allocatable variable with a nonconstant nondeferred
length can still be an automatic data object under 8.3; the attribute
alone does not establish the opposite.

The original note's REAL declarations and mixed
`A(:,:), B, SCALAR` list explicitly distinguish rank specified here,
rank specified earlier and a true scalar. They supply no initialized
payload or allocated bounds. Earlier type specifications are a useful
bounded control setup, not an invented universal requirement that every
legal type/attribute combination must use that exact statement order.

## Entity, scope and lifetime boundaries

Object-name uses the explicit R804/C810 data-object rule, not an arbitrary
designator. A percent-component designator is not the R833 object-name
alternative. Components can have ALLOCATABLE under their own declaration
grammar; that does not make `ALLOCATABLE object%component` a valid statement.
The planned grammar repair names the separately eligible whole object.

An allocatable dummy must have its actual/dummy and explicit-interface
requirements satisfied. Its actual may already be allocated or be
unallocated under 15.5.2.7; do not claim every dummy starts unallocated.
A function result variable may be allocatable, but the value of a function
reference does not itself have that attribute. A called nonpointer result
must be properly defined; declaration admission alone is not evidence
that a result has allocated, returned or been safely used.

ALLOCATABLE is not ALLOCATE. The statement has no executable
`SOURCE=`, `MOLD=` or `STAT=` allocation interface. Allocation by ALLOCATE,
qualifying assignment or MOVE_ALLOC, initial/local-entry allocation status,
argument association, SAVE retention and deallocation keep their defining
owners. An unallocated object supplies no payload, size, bounds, cobounds
or deferred-parameter value just because this statement is accepted.
Only valid inquiry-specific exceptions may be used.

An ALLOCATABLE statement can introduce a local identifier under
19.5.1.4p2, hiding a same-named host entity. In BLOCK it is a declaration
of a construct entity under 11.1.4/19.4. This is different from the
ASYNCHRONOUS statement's scoped-attribute behavior. A type declaration
must make a newly introduced local object legitimate where required;
printing an unchanged host value is not a proof of attribute identity.
USE-associated objects cannot simply be re-attributed ALLOCATABLE in
the accessing scope contrary to 14.2.2p9.
