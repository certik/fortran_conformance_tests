### S7.4.4.4-001: Each character method has a one-to-one collating index map

**Source:** 7.4.4.4 p1; J3/24-007, 18 December 2023, PDF 86, printed 72, lines 9-12. **Class:** Effect.

**Definition:** For each character kind the processor defines a collating sequence giving a one-to-one
correspondence between its characters and the integers from zero through N-1, where N is
the size of that character set. CHAR and ICHAR convert according to this kind-specific
map. The contiguous abstract index domain does not require consecutive code positions
for letters or digits, ASCII native order, UTF-8, a storage encoding or any graphic
shape.

CHAR's argument must lie in the selected method's index domain. ICHAR requires a
representable one-character argument, and its result integer kind must be capable of
representing N itself, not merely one sampled code or N-1. Same-kind character
relational operations use the corresponding collating order with their separately
specified padding rules. Neither a guessed N nor a small observed ICHAR result
establishes the result-kind premise.

**Diagnostic obligation:** not-required.

**Facets:** `finite-round-trips`, `native-relational-consistency`, `method-cardinality-and-result-kind`, `whole-method-mapping`.

**Oracle:** Draft plan only. Inverse identities and equality/order consistency are conditional
finite witnesses with explicit domain and integer-capacity proofs. The mandatory
default-order effects below use native one-character relational comparisons instead of
unsafe ICHAR calls, so their execution is not gated away by missing cardinality
documentation.

**Oracle limitation:** No full repertoire, character storage size or source/display interface is inferred from
codes. The round trips can be mutually consistent while a separate named-set mapping is
wrong; S7.4.4.4-003 therefore keeps its independent external-reference obligation. Do
not test out-of-domain CHAR, insufficient ICHAR result kinds, unrepresentable characters
or undefined results as mandatory rejection/trap cases.

**Dependencies:** 7.4.4.1 and 7.4.4.2 p3 (PDF 84); 10.1.5.1 p6 and 10.1.5.5.1 p7-p8/NOTE 2 (PDF 175,
180-181); 16.9.52 p3-p5 and 16.9.105 p3-p5 (PDF 394, 419); 16.9.181 (PDF 454-455) can
select a result kind only after a sufficient range request is proved. 4.2 p6-p8 (PDF 47)
supplies the separate processor-documentation context.

### S7.4.4.4-002: Default character order satisfies exactly five listed constraints

**Source:** 7.4.4.4 p2 and its five bullets; PDF 86, printed 72, lines 13-20. **Class:** Effect.

**Definition:** For default character, the 26 uppercase letters are strictly ordered alphabetically, the
ten digits are strictly ordered by their listed digit order, and the 26 lowercase
letters are strictly ordered alphabetically. Blank precedes the digits and uppercase
letters, with either the whole digit interval before uppercase or the whole uppercase
interval before digits. Independently, blank precedes digits and lowercase letters, with
either interval before the other. Both alternatives in each of the two disjunctions are
permitted.

These constraints specify relative order, not consecutive integer codes or distances.
They do not fix the relative placement of upper- and lowercase letters, punctuation or
other characters. They are not imposed as a general rule on every nondefault character
kind.

**Diagnostic obligation:** not-required.

**Facets:** `uppercase-order`, `digit-order`, `blank-digit-uppercase-alternatives`, `lowercase-order`, `blank-digit-lowercase-alternatives`.

**Oracle:** Five unconditional run cases check all 25 uppercase, nine digit and 25 lowercase
adjacent inequalities and both complete alternatives in each blank/digit/letter boundary
disjunction. Native one-character comparisons avoid an unproved ICHAR result-kind
capacity; no intercase order or contiguous code spacing is asserted. Direct case IDs:
S7_4_4_4_002_valid__blank_lowercase, S7_4_4_4_002_valid__blank_uppercase,
S7_4_4_4_002_valid__digits, S7_4_4_4_002_valid__lowercase,
S7_4_4_4_002_valid__uppercase.

**Oracle limitation:** There is no negative-source twin for these processor effects. The finite comparisons
cover all required adjacent letter/digit inequalities and boundary chains, not any
unconstrained order. No default N, character-code width, ASCII native encoding,
contiguous letters/digits or graphic appearance is asserted.

**Dependencies:** 6.1.2-.5 (PDF 67-68), 7.4.4.2 p2-p3 (PDF 84), 7.4.4.4 p1/p3 (PDF 86), 10.1.5.1 p6 and
10.1.5.5.1 p7-p8 (PDF 175, 180-181). The direct relational route deliberately avoids
16.9.105 p5's ICHAR result-kind requirement (PDF 419).

### S7.4.4.4-003: Named ASCII and ISO 10646 methods retain their specified collating sequences

**Source:** 7.4.4.4 p4; PDF 87, printed 73, lines 1-3. **Class:** Effect.

**Definition:** The ASCII character kind uses the ISO/IEC 646:1991 International Reference Version
sequence, called the ASCII collating sequence here. The ISO 10646 character kind uses
the ISO/IEC 10646 sequence. These are conditional obligations for those methods, not a
requirement that either optional kind exist or that default character be ASCII.
ACHAR/IACHAR use the ASCII mapping under their own argument, representation and result
premises; CHAR/ICHAR use the selected/native method's mapping.

**Diagnostic obligation:** not-required.

**Facets:** `ascii-method-witness`, `iso10646-method-witness`, `external-collation-reference`.

**Oracle:** Draft plan only. The ASCII X position has a direct pinned canonical example. The ISO
witness and broader tables need independent external-reference/source-interface
evidence, not compiler agreement or memory. Optional named-kind support is checked
separately; any source-interface profile states only its finite decoding premise.

**Oracle limitation:** For ACHAR, ASCII positions 0 through 127 have the specified character only if
representable in the result kind; other cases are processor dependent. IACHAR requires
length one and has specified ASCII positions only for ASCII members; otherwise its
result is processor dependent. No arbitrary CHAR code, non-ASCII IACHAR fixed value,
native/default ASCII promise or ICHAR result-kind shortcut is licensed. A selected kind
may equal default; no distinction is presumed.

**Dependencies:** 7.4.4.1 p3 (PDF 84); 16.9.3 p3-p6 (PDF 377), 16.9.98 p3-p6 (PDF 416), 16.9.52 (PDF 394),
16.9.105 (PDF 419), 16.9.180 p5-p6 (PDF 454), and 7.4.3.1 p4 (PDF 80) for bounded
default-integer ASCII results. The informative NOTE 2 is a reference to these contracts,
not an independent new requirement.

### S7.4.4.4-004: Lexical comparison intrinsics use ASCII order under their own premises

**Source:** 7.4.4.4 p5; PDF 87, printed 73, lines 4-6. **Class:** Effect.

**Definition:** LGT, LGE, LLE and LLT compare strings using the ASCII collating sequence; this subclause
guarantees international portability for characters restricted to the Fortran character
set. Their canonical contracts require STRING_A to be default or ASCII character and
STRING_B to have the same kind. A separately supported ISO_10646 or arbitrary nondefault
kind is not automatically an admissible argument kind unless it also is default or
ASCII.

For unequal lengths the shorter string is extended on the right with blanks. Equal and
zero-length strings have the specified nonstrict/strict comparison results. If either
string contains a non-ASCII character, the intrinsic result is processor dependent;
IACHAR's specified consistency relationship still applies to legal one-character
arguments. Native relational operators instead use the kind's processor collating
sequence and are not interchangeable with the LGE family.

**Diagnostic obligation:** not-required.

**Facets:** `default-ascii-order`, `ascii-kind-order`, `padding-and-empty`, `fortran-repertoire-portability`, `iachar-consistency`, `nonascii-result-domain`.

**Oracle:** Three run programs check all four lexical procedures with the pinned ONE/TWO examples,
reversals/equality, blank extension and zero-length outcomes. The separate O/T/X
one-character witness checks IACHAR consistency and ACHAR inversion only in the bounded
ASCII domain. Native relational order is not its oracle; optional ASCII-kind and full
external mapping work remains pending. Direct case IDs: S7_4_4_4_004_valid__default,
S7_4_4_4_004_valid__iachar_consistency, S7_4_4_4_004_valid__padding_empty.

**Oracle limitation:** No compile-only downgrade is allowed for these run effects. Non-ASCII results are not
replaced by a guessed fixed order, and unsupported lexical intrinsics are failed
observations rather than optional properties. The broader ACHAR(IACHAR(c))
default-representability promise and IACHAR consistency do not make every outside-ASCII
numeric result fixed. No identical-answer requirement between native relational and
lexical functions is imposed.

**Dependencies:** 6.1 (PDF 67-68); 16.9.124-.127 p3-p5 and their zero-length notes (PDF 427-428); 16.9.98
p3-p5 and 16.9.3 p5 (PDF 416, 377); 10.1.5.1 p6 and 10.1.5.5.1 p7-p8/NOTE 2 (PDF 175,
180-181); 7.4.3.1 p4 (PDF 80); 16.9.180 (PDF 454).
