### S6.1.6-001: Additional representable graphic characters have restricted occurrence contexts

**Source:** 6.1.6 p1 (J3/24-007 PDF 68, printed 54, lines 4-5; heading at line 3). **Class:** Restriction.

**Definition:** Given additional characters that the processor can represent, their occurrence is
limited to comments, character constants, input/output records, and character string
edit descriptors. In the 6.1.1 partition, other characters are a graphic-character class
outside letters, digits, underscore, and the Table 6.1 special characters. This
paragraph does not require any particular additional repertoire, Unicode support, input
encoding, or nondefault character kind. It does not classify ordinary control characters
as other graphic characters or forbid character variables from holding values supplied
by the character-type rules.

The enclosing context must still be legal. Free-form literal rep-char is graphic;
fixed-form literal rep-char can be any character of the appropriate processor set, with
processor restrictions on control characters allowed. Comments inherit character-context
admissibility under 6.3.1 p2 and have different free/fixed initiation rules. Character
string edit descriptors use a literal without a kind parameter and are output-only.
Formatted records contain representable characters and can be subject to
control-character prohibitions. Neither comments nor arbitrary I/O records become
character contexts under 3.21, which names only literals and character string edit
descriptors.

For an actual source-character or source-form violation, the diagnostic basis is the
capability required by 4.2 p2(5), not merely the word shall in this paragraph. A
permitted extension does not remove that capability, but the standard does not require a
fatal rejection in every mode. The 4.2 p3 exemption for additional forms in a format
specification outside a FORMAT statement must also be preserved. No invalid case is
claimed until its source-character identity, representability assumptions, source form,
prohibited occurrence, and applicable reporting configuration are established.

**Diagnostic obligation:** required.

**Facets:** `free-form-comment-admission`, `fixed-form-comment-admission`, `free-form-character-constant-admission`, `fixed-form-character-constant-admission`, `free-form-edit-descriptor-admission`, `fixed-form-edit-descriptor-admission`, `iso10646-internal-input-record`, `iso10646-internal-output-record`, `external-formatted-input-record`, `external-formatted-output-record`, `free-form-prohibited-source-context`, `fixed-form-prohibited-source-context`.

**Oracle:** Two independent positive controls use the already registered iso10646 profile. Its
separate program asks SELECTED_CHAR_KIND('ISO_10646'); an unavailable kind yields the
runner's profile skip, whereas a failed probe remains a failure. After that
precondition, CHAR(937,kind=ucs4) and CHAR(9731,kind=ucs4) construct the ISO 10646
graphics U+03A9 and U+2603 without non-Fortran source bytes. Each constructed value has
length one by the CHAR contract, not by counting a multibyte source spelling. The output
program writes a four-character ISO-kind internal record through A1,A2,A1 fields, then
checks both distinct outer characters and the two-character middle field. The input
program initializes a different record with reversed outer characters and different
middle data, reads the three fields, and checks their exact same-kind character values
and distinctness. Both guard IOSTAT before accessing transferred data. All record
lengths and substring bounds are fixed and valid; no allocation, association, or absent
data is involved.

**Oracle limitation:** These two cases are conditional admission controls for the I/O-record context of a
restriction, not full effects or source-representability evidence. Their source contains
only the Fortran repertoire. They cannot cover source literals containing additional
graphics, comments, edit strings, forbidden source placements, default-kind extra
repertoire, external encoding, or rendering. The finite oracle relies on the canonical
CHAR, character equality, assignment, and character-editing semantics; it does not
certify every ISO character or every character kind. Direct character equality avoids
ICHAR's separate result-kind requirement to represent the entire collating-sequence
size. Unsupported ISO kind is an explicit optional-profile skip, not a passed case. The
graphics facets already pending under S6.1.1-001 are unchanged.
