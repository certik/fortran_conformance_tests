### R608: Intrinsic operators comprise nine syntactic categories

**Source:** 6.2.4 R608; J3/24-007 PDF p69, printed p55, lines 14-22. **Class:** Syntax.

**Definition:** The intrinsic-operator syntactic class is the union of power-op, mult-op, add-op,
concat-op, rel-op, not-op, and-op, or-op, and equiv-op. The member spellings are defined
by the corresponding Clause 10 rules, which are restated here for reference. This union
does not by itself specify operand types, numbers of operands, evaluation, or
precedence, nor does membership require that every use be an intrinsic rather than a
defined operation.

**Diagnostic obligation:** required.

**Facets:** `power-op`, `mult-op`, `add-op`, `concat-op`, `rel-op`, `not-op`, `and-op`, `or-op`, `equiv-op`.

**Oracle:** Nine separately compiled positive-control programs admit all nine categories in
conforming intrinsic expressions. Together they use all 23 intrinsic spellings,
including unary and binary add-op contexts. Integer computations, same-kind character
concatenation, integer relations, and logical operations have direct literal result
assertions. Each expression under test is assigned to a result before checking it; the
expected result is not another invocation of the tested expression.

**Oracle limitation:** These are finite syntax/admission controls with runtime self-checks, not independent
coverage of the Clause 10 token definitions, precedence, evaluation order, all operand
type/kind/rank combinations, or generic dispatch. No R608-only malformed-token negative
is manufactured: malformed member spellings belong to their canonical rules, and the one
well-formed nonoperator exclusion in an actual OPERATOR generic context is assigned only
to R609. The absence of a separate invalid file is a testing boundary, not an uncovered
acceptance facet.

**Dependencies:** 4.1.1 explains alternatives and later-clause restatements; 4.1.2 p2 makes associated
constraints apply at every occurrence; 4.2 p2(3) requires diagnostic capability for
syntax violations, not a particular severity or mandatory rejection. Canonical
spellings: 10.1.2.5/R1008-R1010, 10.1.2.6/R1012, 10.1.2.7/R1014, and
10.1.2.8/R1019-R1022 (PDF pp169-171). 10.1.5, including Table 10.2, supplies the valid
intrinsic operand/result premises and the assertion values. R610 and 10.1.6 distinguish
extension uses.

### R609: Defined-operator admits named unary, named binary, and intrinsic extension forms

**Source:** 6.2.4 R609; J3/24-007 PDF p70, printed p56, lines 6-8. **Class:** Syntax.

**Definition:** A defined-operator is a defined-unary-op, a defined-binary-op, or an
extended-intrinsic-op. The first two syntactic classes inherit their canonical Clause 10
definitions and constraints, and the third is supplied by R610. These alternatives can
occupy the defined-operator position of an OPERATOR generic specification. A well-formed
token outside all three classes, such as the assignment symbol, cannot occupy that
position. The union does not itself define a procedure interface or make a particular
operation applicable.

**Diagnostic obligation:** required.

**Facets:** `defined-unary-op`, `defined-binary-op`, `extended-intrinsic-op`, `operator-generic-operand`.

**Oracle:** Use valid explicit interfaces for a named unary function, a named binary function, and
unary and binary intrinsic extensions on derived-type operands. Independent literal
checks establish that each conforming control executes meaningfully. Isolate one
negative with INTERFACE OPERATOR (=): the assignment symbol is a well-formed Fortran
token but not an R609 alternative. Its function has two nonoptional INTENT(IN)
derived-type dummy arguments and an integer result. The minimally repaired control
replaces only that operator-position token by +; both bodies call the helper by its
specific name, so the negative has no additional bad expression or unresolved operator
reference.

**Oracle limitation:** Do not attribute malformed dotted names, excessive operator-name length, reserved
intrinsic/logical spellings, missing interfaces, wrong arity, or forbidden intrinsic
signatures to this union. Those belong to R1004/C1005, R1024/C1006, or Clause 15. The
one negative tests membership in a context that explicitly requires defined-operator,
not every forbidden token. 4.2 requires diagnostic capability; the runner additionally
expects rejection and a source-located error. A compiler accepting with a relevant
diagnostic is not the same observation as silent acceptance.

**Dependencies:** R1004/C1005 in 10.1.2.4 (PDF p169), R1024/C1006 in 10.1.2.9 (PDF p171), and local R610.
R1503/R1506/R1508 and C1504/C1507/C1508 in 15.4.3.2 (PDF pp326-327) supply the
generic-interface context and explicit procedure interfaces. 15.4.3.4.2 p1 (PDF p329)
supplies nonoptional data dummies, INTENT(IN) or VALUE, one/two arguments,
non-assumed-length results, and signatures distinct from intrinsic operations.
10.1.6.1-2 (PDF pp181-182) supplies applicability and function-defined interpretations;
no type-bound or generic-resolution coverage is inferred. 4.2 p2(3) supplies the
diagnostic-capability obligation.

### R610: An intrinsic extension retains an intrinsic operator spelling

**Source:** 6.2.4 R610; J3/24-007 PDF p70, printed p56, line 11. **Class:** Syntax.

**Definition:** The extended-intrinsic-op syntactic class is an alias for intrinsic-operator. It
introduces no additional operator spelling. In the R609 alternative this permits an
intrinsic operator token to identify a defined operation, provided the separate
expression and procedure-interface requirements are met. It neither authorizes replacing
an existing intrinsic signature nor establishes which function is selected.

**Diagnostic obligation:** required.

**Facets:** `power-op`, `mult-op`, `add-op`, `concat-op`, `rel-op`, `not-op`, `and-op`, `or-op`, `equiv-op`.

**Oracle:** Ten positive-control programs use explicit OPERATOR interfaces for all nine inherited
categories. Unary and binary add-op extensions are separate programs; not-op is unary
and the other sampled operations are binary. Every extension uses declared scalar
derived-type operands, matching nonoptional INTENT(IN) dummies, and an explicit
non-assumed-length result. Their signatures differ from all intrinsic signatures.
Literal integer, character, or logical checks test the results of the chosen functions;
the relational extension samples < rather than duplicating every relational spelling.

**Oracle limitation:** This alias has no independent rejection boundary once R608 and its member grammar are
fixed, so no R610_invalid file is forced. Wrong extension arity, an intrinsic-signature
collision, type-bound binding restrictions, generic ambiguity, and operand association
defects are owned by Clause 15/10, not this alias. The controls do not claim all
extension signatures, every relational synonym, mixed types, ranks, kinds, precedence,
or dispatch semantics. They do not require a processor-dependent kind, floating-point
tolerance, collating sequence, or optional feature.

**Dependencies:** R608 supplies the nine categories and its Clause 10 references supply their spellings.
5.5.6 (PDF p66) distinguishes intrinsic and additional operators. 10.1.5.1/Table 10.2
(PDF p175), 10.1.6.1-2 (PDF pp181-182), and 15.4.3.4.2 p1-p3 (PDF p329) provide the
valid intrinsic/defined-operation premises, intrinsic-compatible arity, distinct
signatures, and interpretations. 15.4.3.2 supplies the explicit generic interfaces.
These dependencies are not locally reauthored requirements. Syntax diagnostics inherit
4.2 p2(3); the alias is not an additional diagnostic policy.

## Fixture plan and coverage boundary

The finite plan has **22 facets**: nine R608 category facets, four R609
union/context facets, and nine R610 category facets. Every declared facet
has a fixture; no pending facet is hidden by a compiler outcome.

| Requirement | Programs / isolated cases | Scope |
| --- | ---: | --- |
| `R608` | 9 positive controls | All nine intrinsic categories and all 23 intrinsic spellings |
| `R609` | 5 positive controls, 1 negative | Named unary/binary forms, unary/binary extensions, and the operator-position exclusion/repair |
| `R610` | 10 positive controls | All nine inherited categories in valid extensions; separate unary/binary add-op programs |
| **Total** | **24 positive controls, 1 negative** | **25 independently compiled executions** |

All fixtures are ordinary free-form `.f90` programs; no manifest fixture
is necessary. Their leading headers credit only the annotated rule and
facet. All valid fixtures explicitly use `evidence: positive-control`:
runtime assertions make the controls meaningful but do not turn a
high-level union/alias into an independently tested evaluation rule.

The intrinsic controls use small default integers, default logicals,
and default-kind characters. Division is exact and nonzero, exponentiation
stays within the required integer range, and character comparisons check
equality rather than a processor's collating order. Expected results are
literals, not calls to the tested expression or its implementing function.
Logical checks use `MERGE(1, 0, result)` against literal truth-table entries;
this selects an integer value without assuming a logical storage encoding
or reusing the logical operator under test as the assertion.
No optional kind, floating-point representation, arbitrary tolerance,
coarray facility, or processor profile is needed. All cases predate
Fortran 2023, so a reported Fortran 2018 reference mode is sufficient for
these controls.

Named operators have short letter-only names that are neither intrinsic
operators nor logical literals. All operator procedures have explicit
interfaces, one or two nonoptional `INTENT(IN)` data dummies, and results
without assumed character length. Derived-type operands distinguish each
intrinsic extension from every intrinsic signature; dummy and actual
types and ranks match. The intrinsic arity is preserved. Functions have
no observable side effects or evaluation-order dependencies.

R610 samples `<` for the relational extension, rather than duplicating
all six relations and their alternate spellings. The other extension
fixtures use `**`, `*`, `/`, unary/binary `+` and `-`, `//`, `.NOT.`,
`.AND.`, `.OR.`, `.EQV.`, and `.NEQV.`. Neither these examples nor the
intrinsic spelling controls claim all operand type/kind/rank combinations,
generic resolution, type-bound dispatch, or precedence.

## The isolated diagnostic and its repair

`R609_invalid__assignment.f90` places the well-formed assignment symbol
in `INTERFACE OPERATOR (=)`, where R1508 explicitly requires a
`defined-operator`. It belongs to none of R609's alternatives. The
enclosing program and helper interface are otherwise conforming. In
particular, its two derived-type dummy arguments would make the repaired
`+` a legitimate extension, not a forbidden replacement for intrinsic
integer addition.

`R609_valid__assignment_repair.f90` changes only that operator-position
token to `+` (apart from test metadata and the diagnostic marker). Both
program bodies call the helper by its specific name and check the literal
result. There is no additional malformed expression, missing procedure,
or unresolved operator use. The invalid header claims only the
`operator-generic-operand` facet and contains one explicit case.

This is a syntax violation requiring diagnostic capability under
4.2 p2(3). That does not require fatal rejection, a rule number, or a
particular severity. The suite's stronger rejection/source-location
contract is recorded separately in compiler observations.

There is no independently isolated alias violation requiring an
`R608_invalid` or `R610_invalid` file. Bad member-token spellings belong
to the canonical Clause 10 rules; excessive or reserved dotted names
belong to C1005/C1006; invalid procedure interfaces and intrinsic-signature
collisions belong to Clause 15. Those are testing boundaries, not
invented pending facets or duplicated diagnostics.
