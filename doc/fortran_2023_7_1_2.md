### S7.1.2-001: Use nonintrinsic type names only where accessible

**Source:** 7.1.2 p3, PDF 75, printed 61, lines 13-14; type origins on lines 11-13. **Class:** Restriction.

**Definition:** A use of a nonintrinsic type name requires that name to be accessible at the use. This
applies to derived, enum and enumeration types, including types supplied by intrinsic
modules. It concerns the identifier's accessibility, not the accessibility of every
component or type-bound procedure and not mere availability of a value of that type.

**Diagnostic obligation:** context-dependent.

**Facets:** `local-derived-name`, `host-derived-name`, `use-renamed-derived-name`, `enum-name-access`, `enumeration-name-access`, `intrinsic-module-type-access`, `nonintrinsic-access-use-graph`.

**Oracle:** Three independent positive controls declare an ordinary derived type locally, access it
in an internal procedure by host association, and access a public module type through a
renamed USE name. Initialized integer payloads are checked, so no undefined component or
dynamic pointer is read.

**Oracle limitation:** These are conforming-use controls, not negative evidence. The underlying restriction
remains real and its missing exclusion/use-graph evidence remains pending. 4.2 p2(3) can
apply through numbered constraints such as C795; p2(6) concerns Clause 19 scope
inconsistencies in a submitted program. Neither this prose sentence nor a single
compiler invocation establishes mandatory fatal rejection or every applicable reporting
mode.

**Dependencies:** 7.5.2.2 p1-p2 (PDF 89) and 8.5.2 p1-p4 (PDF 120) separate type-name and component
accessibility. 7.5.9/C795 (PDF 106) and 7.5.10/C7107 (PDF 107) retain their official
owners. 19.1 p2/p4 (PDF 548), 19.5.1.3-.4 (PDF 553) and 14.2.2 supply scope, use
renaming and host association. 7.6.1-.2 (PDF 109-113) distinguishes enum types, integer
enumerators and enumeration types.

### S7.1.2-002: Intrinsic types remain accessible

**Source:** 7.1.2 p3, PDF 75, printed 61, line 14. **Class:** Effect.

**Definition:** The five intrinsic types are always accessible. They do not require a USE association
that imports their type names; a module's default PRIVATE accessibility does not remove
intrinsic type availability. This does not make every kind value supported or every
intrinsic procedure name immune to ordinary scope rules.

**Diagnostic obligation:** not-required.

**Facets:** `local-intrinsic-keywords`, `private-module-intrinsic-keywords`, `intrinsic-access-use-graph`.

**Oracle:** Two programs use all five intrinsic type keywords without importing type names, one in a
main program and one for private module objects exposed only through a checking
procedure. Each object's initialized value is checked. Default real and complex controls
use zero, and character equality uses only Fortran characters.

**Oracle limitation:** No storage width, kind number, character encoding or floating-point representation is
assumed. The fixtures do not test the unrelated accessibility of intrinsic procedure
identifiers. Acceptance alone does not establish that all other types have been
classified correctly.

**Dependencies:** 7.1.2 p2 names the five categories. 7.4.1/R704-R706 (PDF 80), 7.4.3.3 (PDF 83), 7.4.4.2
(PDF 84-85), 7.4.5 (PDF 87) define their specifiers/defaults. 8.5.2 p4 (PDF 120)
qualifies PRIVATE as identifier accessibility.
