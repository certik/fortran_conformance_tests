## Common admission and diagnostic contract

The initial fixture tier is F2023 with ordinary default INTEGER,
LOGICAL and CHARACTER where possible, not assumed numeric kind values.
Module providers, complete procedure interfaces/definitions and clients
must be built in order. A required facility that a processor does not
implement is a failure or unresolved corroboration, not an optional-profile
success. Actual standard modes, capability premises and any image launcher
must be recorded before later native qualification.

For C856-C860, 4.2p2(3) requires reporting capability for the numbered
violation. It does **not** require fatal rejection, a literal C-number in
printed output, or particular diagnostic wording. Each prospective
negative is paired with a source-minimal conforming repair and a
role-specific cause. Removing the sole PROTECTED specification while
retaining all other eligibility conditions is the default C859/C860
repair. A PRIVATE substitution, wrong entity, inaccessible provider,
invalid interface, unsupported feature, crash or resource error is not
that repair or corroboration.

A negative isolates one forbidden client context. Paired notification,
event or lock operations use separate variants, with legal owner-host
setup/drain APIs that take no protected object as a defining actual.
Do not count one diagnostic as evidence for several offending uses.

Direct valid numbered controls are `positive-control`, normally compile
admission. The S restrictions use conforming positive controls or explicit
source-use/optional-policy gates, never an invented standard-required
failure from a prose `shall`. No invalid program is run as a required trap.
Future runtime controls need complete entry/return/completion observers,
defined values, independent literals and full-parent qualification;
success of a fragment or of another compiler configuration is insufficient.

## Scope, subject and alias premises

PROTECTED is not PRIVATE. PUBLIC accessibility must make the selected
entity available to the client; ordinary references remain possible.
USE renaming and re-export do not remove the attribute. C856 permits
specification only in the module specification part; this is necessary,
not sufficient. Respecifying PROTECTED on a USE-associated entity is still
restricted by 14.2.2p9.

The p2 exception concerns the **module where the attribute is given** and
its actual submodule descendants. A foreign module which USEs the entity
does not become that owner. A setter in the provider or a genuine
descendant accesses the object by host association. The client must not
pass the protected nonpointer itself to an OUT/INOUT dummy, or the
protected pointer to a pointer OUT/INOUT dummy, merely because the callee
is in the owner module: C859/C860 apply at that caller context.

The p3 propagation rule is normative and covers all actual subobjects.
Under 9.4.2p5 a pointer component is a subobject in an association-status
context, but its target is not a subobject of the containing object.
Changing a protected pointer's association is different from defining its
separately unprotected, live, definable target. A target that independently
has PROTECTED, is not definable, is absent, is dead, or is subject to
conflicting dummy-argument restrictions cannot be mutated merely through
an ordinary pointer alias.

An independent pointer `q => p` shares a target, not the pointer object.
It is different from a pointer dummy argument associated with `p` under
15.5.2.4p5. The latter does not supply a loophole for changing the protected
actual's association through unspecified INTENT. Conversely, an ordinary
nonpointer INTENT(IN) dummy is the clean readonly control for a protected
nonpointer actual; a pointer INTENT(IN) dummy additionally requires a valid
pointer-assignment target under 15.5.2.8.

For item (11), the first bounded selector witness is a definable scalar
variable in ASSOCIATE. Replacing it with `x+0` does not repair a writable
associate, because C1101/11.1.3.3 still apply. A directly imported module
variable cannot simply be declared assumed-rank for SELECT RANK:
8.5.8.7 C839 and 11.1.10.1 C1155 must hold. An argument-mediated rank
example needs its own identity/caller proof and is not automatically
another C859 selector case. SELECT TYPE and CHANGE TEAM extensions remain
explicit eligibility gates rather than invalid `_valid` controls.

EVENT, LOCK and NOTIFY contexts use the genuine intrinsic types and
required coarrays. C1603-C1614 and the allowed statement contexts are
retained; the negative changes only protection. The client NOTIFY= variant
uses `payload[THIS_IMAGE(),NOTIFY=notice] = 17`, an unprotected payload and
a noncoindexed notify-variable, followed by an owner-host drain. A separate
client NOTIFY WAIT variant has an owner-host preparation notification.
EVENT and LOCK alternatives follow the same single-forbidden-use pattern.
No private component/count representation is read. A processor's failure
to implement the repaired facility does not corroborate C859.

Zero-sized arrays and zero-length strings are always defined under
19.6.2, but still can appear in a forbidden variable-definition context.
That rule supplies neither allocation, valid association nor presence,
and does not exempt a protected object from C859.

## C860 families and lifetime exceptions

All four families of 19.6.8 remain explicit: NULLIFY, data/procedure
pointer assignment, ALLOCATE/DEALLOCATE, and actual association with an
OUT/INOUT pointer dummy. Procedure pointers can be nullified,
pointer-assigned or passed to matching procedure-pointer dummies; they
are not data allocation objects. Ordinary pointer-target assignment is
not a pointer-association context by itself.

The p2 lifetime exceptions are not observable Boolean status values.
For the other-route case, an independent alias may legally deallocate
the whole matching target created by ALLOCATE. Direct deallocation through
the imported protected pointer is still excluded. For BLOCK/RETURN/END
target loss, the complete argument/target-lifetime premises must first be
established. No ASSOCIATED inquiry, pointee reference or call is allowed
through the resulting undefined association.

The pending legality controls therefore observe ordinary live snapshots
and entry/exit/reset markers, then call an **owner-side unconditional
reset** before any subsequent association inquiry. They do not claim to
observe undefined association. An outside caller cannot NULLIFY the
protected pointer just to make its inquiry safe. Procedure-pointer
controls use live module targets; an internal-procedure-host-death
combination requires a separate source argument and is not silently
included as a retention or lifetime-extension case.

### C856: PROTECTED is specified only in a module specification part

**Source:** 8.5.15 C856; J3/24-007, 18 December 2023, physical PDF131. **Class:** Restriction.

**Definition:** The PROTECTED attribute may be specified only in the specification part of a module. A
main program, submodule, procedure, BLOCK or interface body's own specification part is
not the module specification part, even when textually nested in a module.

**Diagnostic obligation:** required.

**Facets:** `module-specification-forms`, `main-scope-excluded`, `procedure-scope-excluded`, `block-scope-excluded`, `interface-body-excluded`, `submodule-scope-excluded`.

**Oracle:** For isolated numbered violations require detection/reporting under 4.2p2(3), with an
accepted complete minimal repair and cause tied to the PROTECTED declaration's scope.
Valid controls are compile admission, not runtime protection evidence. R858 and
type-declaration syntax keep their own owners.

**Oracle limitation:** Module placement is necessary, not sufficient: C857/C858 and USE-associated attribute
restrictions still apply. Neither a PRIVATE substitution nor a missing
provider/interface is a conforming repair. No mandatory fatal rejection, rule-code
spelling or compiler-specific wording follows.

**Dependencies:** 3.120;5.2.1;8.2;8.6.13;14.2.1-.3;15.6.2.5;19.5.1.4;4.2p2.

**Definition:** An entity with PROTECTED must be a variable or a procedure pointer. A data pointer is a

**Oracle limitation:** Direct DEALLOCATE through this pointer is not the p2 other-route exception. A

### S8.5.15-001: A protected nonpointer is not definable outside its defining module and descendants

**Source:** 8.5.15 p2 scope qualification and first bullet; J3/24-007, physical PDF131. **Class:** Restriction.

**Definition:** Other than within the module in which the entity is given PROTECTED or within any
descendant of that module, a protected nonpointer object is not definable. Association
and aliasing do not turn a nondefinable ultimate object into a definable one. This scope
rule is not PRIVATE accessibility.

**Diagnostic obligation:** not-required.

**Facets:** `module-host-setter-control`, `descendant-host-setter-control`, `foreign-host-route-restriction`, `alias-to-protected-target-restriction`.

**Oracle:** Conforming scope controls are positive-control evidence, not a proof of every forbidden
definition. For a concrete forbidden form that satisfies C859, retain C859 primary
ownership and its required reporting basis; a p2-only proposal needs an independently
declared additional diagnostic policy, a valid minimal repair and the exact
ultimate-object/cause argument.

**Oracle limitation:** The owner is the module where the attribute is given, not any module that imports the
entity. Host association retains attributes but does not make a foreign host part of
that owner tree. No blanket diagnostic obligation, exclusive-setter rule, copy/address
oracle or aliasing waiver is inferred.

**Dependencies:** 8.5.2;8.5.15C859/p3;9.2;9.4.2;10.2.1.2p3;14.2.1-.3;15.6.2.5;15.5.2.4/.5/.8/.14;19.5.1.3/.4;4.2p2.

### S8.5.15-002: A protected pointer's association is preserved outside its owner subject to exact target-lifetime exceptions

**Source:** 8.5.15 p2 scope qualification, second bullet and its exceptions; J3/24-007, physical PDF131. **Class:** Restriction.

**Definition:** Outside the defining module and its descendants, a protected pointer's association
status must not be changed, except that it may become undefined when its target is
deallocated other than through it, or becomes undefined on BLOCK completion or
RETURN/END. This protects association, not an independently definable unprotected
target's value, and does not prolong any target or procedure-host lifetime.

**Diagnostic obligation:** not-required.

**Facets:** `module-descendant-association-control`, `unprotected-target-definition-control`, `no-intent-pointer-alias-restriction`, `other-route-deallocation-context`, `block-target-end-context`, `return-end-target-context`, `procedure-call-control`.

**Oracle:** Numbered C860 contexts retain C860 ownership. These conforming controls exercise owner
access, legal target-value operations or allowed lifetime-ending contexts, without
claiming direct observation of undefined status. Every future runtime control needs
complete calls, defined values, live association before inquiries, independent
literals/visits/completion and supported-mode qualification; compiler consensus is not
its source oracle.

**Oracle limitation:** Undefined association is not defined disassociation and cannot be queried with
ASSOCIATED. Target deallocation must satisfy 9.7.3.3, not deallocate an ordinary static
or allocatable target through a pointer. The protected pointer cannot be reset by an
outside NULLIFY merely to make an inquiry safe. Any proposed outside-owner
internal-procedure-host-death example needs its own p2/19.5.2.5(8) source argument and
remains outside this packet's finite contexts.
