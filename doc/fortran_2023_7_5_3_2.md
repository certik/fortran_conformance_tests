### S7.5.3.2-001: A nonextended type's parameter order follows its header list

**Source:** 7.5.3.2 p2, first sentence; J3/24-007, 18 December 2023, PDF 92, printed 78, line 14. **Class:** Effect.

**Definition:** For a nonextended derived type, parameter order is the order of names in the defining
TYPE header list. It is not the order of parameter-definition statements, the order
within a later definition list, alphabetical order, or a rule that all KIND parameters
precede all LEN parameters. Positional derived-type specifiers use this ordering subject
to their own value, omission and keyword conditions.

**Diagnostic obligation:** not-required.

**Facets:** `header-position-values`, `definition-statement-order`, `declarator-list-order`, `mixed-kind-length-order`, `specifier-use-graph`.

**Oracle:** Four bounded run plans use distinct exactly representable integer values and direct
parameter inquiries to distinguish header order from independent body ordering. Typed
integer dummies and guarded component-size checks may supplement the inquiry values.
Every concrete fixture still requires independent review.

**Oracle limitation:** No negative or compulsory diagnostic is manufactured for this prose interpretation.
Reordering body declarations must not introduce a forward-reference default expression.
No storage-layout, numeric kind ordering, intrinsic generic-resolution or nonzero real
approximation premise is used. Keyword syntax and argument omission retain their
canonical owners.

**Dependencies:** R727/C736, PDF 88; R732-R734/C746-C747, PDF 91-92; 7.2, PDF 76; 7.5.9/R754 and

### S7.5.3.2-002: An extension retains its parent's parameter order before its local header parameters

**Source:** 7.5.3.2 p2, second sentence; PDF 92, printed 78, lines 14-17. **Class:** Effect.

**Definition:** An extended type's parameter order consists of its parent's parameter order followed by
any additional parameters in the order of the extending definition's TYPE header list.
Parent order is preserved recursively through ancestors. An extension can add no local
parameters while retaining inherited ones; inherited parameters are not redeclared as
new local header entries.

**Diagnostic obligation:** not-required.

**Facets:** `parent-prefix`, `local-header-suffix`, `inherited-only-extension`, `multi-generation-order`, `inheritance-and-specifier-use-graph`.

**Oracle:** Four bounded runtime witnesses distinguish the inherited prefix and local suffix through
exact parameter values, including a no-new-parameter extension and a deeper chain. They
use only ordinary extensible types and source-valid parameter specifications.

**Oracle limitation:** The parent must be a previously defined extensible type, and local names/definitions
still satisfy C736/C746/C747 and inheritance name rules. Type-parameter order does not
imply physical component order or identical type identity across definitions. Missing
PDT implementation is a failed observation, not a reason to replace run effects by
compile controls.

**Dependencies:** 7.5.7.1-.3 and inheritance notes, PDF 104-105; R727/C737, PDF 88; R732/C746/C747, PDF
91; 7.5.9, PDF 106-107; 9.4.5, PDF 153. The concurrent definition/identity source unit
remains a separate owner and review.
