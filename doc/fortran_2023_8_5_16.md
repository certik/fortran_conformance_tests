## What SAVE does and does not preserve

p1 and p2 specify **association status, allocation status, definition
status and value**, with their actual entity/event applicability. They
separately cover RETURN/END of a program unit/subprogram and termination
of a BLOCK. A saved local of a subprogram is shared by all its instances;
the same is true for a saved variable of a BLOCK within that subprogram.
Repeated sequential calls alone do not establish the simultaneous
instance-sharing provision.

The initial effect designs use explicitly saved local data variables,
complete controllers and independent phase/depth/visit/completion
observers. Ordinary nonempty values are defined before the first read.
The independent literals are 11/17 for scalar retention and
[11,13]/[17,19] for nonempty allocation data; these are proposals, not
measurements. The existing default-initialization contrast described
below has its own 3/9 literals and must not be copied or rewritten to
match these illustrative values.

Association inquiries require defined association; disassociation is a
defined association status but does not permit dereference. ALLOCATED
precedes every size/bounds/data inquiry on an allocatable. An allocated
empty object is not an unallocated object, and 19.6.2's always-defined
zero-size/zero-length values do not prove SAVE, allocation or argument
presence. A pointer association to a zero-sized target is not substituted
for the nonempty ASSOCIATED identity witness.

SAVE does not initialize an otherwise undefined variable, freeze a
target's value against legitimate later definitions, make a dummy
argument present, or extend the lifetime of an unsaved target. The
exceptions explicitly refer to 19.5.2.5(6) and (7). No pointer inquiry
or data reference observes the undefined status after target death.
Procedure pointers are admitted by C861, but their interface and
procedure-host lifetime rules retain 15.4.3.6, 15.6.2.4 and 19.5.2
ownership; saved storage is not a closure-lifetime extension.

There is no source promise about an address, stack/static layout, copy
count or ABI. Explicit deallocation, INTENT(OUT), intrinsic assignment
and other finalization events retain their own rules. No absence-of-
finalization output alone is used as a retained-value oracle. No value
is read outside a BLOCK's scope merely because its object is saved, and
no post-END PROGRAM/image-termination observer is proposed.

## Common-block scope consistency

S8.5.16-003 retains the exact antecedent: SAVE in **any non-main,
non-module, non-submodule scoping unit** requires SAVE in every
nonexempt scoping unit declaring that common block. The relevant fact
is possession of the attribute, not the presence of its keyword.
Implicit SAVE only in the three exempt scope kinds does not trigger
that antecedent by itself.

The finite contrasts use named, nonempty common blocks with matching
ordinary INTEGER storage sequences. The complete repair of a missing
nonexempt SAVE is to add a block-level specification in the missing
scope, not SAVE on a member. No BIND implication or other hidden source
of SAVE is allowed in the proposed missing-attribute negative.

This is a prose program restriction. It does not independently require
a compiler to reject or diagnose the complete multi-scope program.
A negative needs a separate reviewed diagnostic-policy or exact
numbered/scope basis, a source-minimal conforming repair and a
role-specific cause. It is not executed as a required trap.

Blank common has its separate nonpointer-retention rule in 8.10.2.5 and
19.6.6. Its retention is not proof of SAVE, and this packet does not
invent `SAVE //` as a valid named-block specification. Likewise, another
active scope referencing a named block can affect its lifetime; a
main/common declaration must not silently turn a purported retention
test into an always-active-storage control.

### S8.5.16-001: Saved local variables retain the specified state across RETURN or END and are shared across subprogram instances

**Source:** 8.5.16 p1, both sentences and the pointer-target exception; J3/24-007, physical PDF132. **Class:** Effect.

**Definition:** A saved local variable of a program unit or subprogram retains its association status,
allocation status, definition status and value after RETURN or END, except for a pointer

**Diagnostic obligation:** not-required.

source packet.

**Oracle limitation:** There is no portable direct assertion that an undefined variable remains undefined.

saved-entity/host-lifetime semantics retain C861, 15.4.3.6, 15.6.2.4 and 19.5.2

### S8.5.16-002: Saved BLOCK locals retain the specified state across termination and are shared across containing subprogram instances

**Source:** 8.5.16 p2, both sentences and the pointer-target exception; J3/24-007, physical PDF132. **Class:** Effect.

**Definition:** A saved local variable of a BLOCK retains its association status, allocation status,
definition status and value after the construct terminates, except for a pointer whose
target becomes undefined under 19.5.2.5(7). If that BLOCK is within a subprogram, the
variable is shared by all instances of the subprogram. Retained storage does not extend
the name's scope.

**Diagnostic obligation:** not-required.

**Facets:** `same-block-defined-values`, `block-live-pointer-association`, `block-disassociated-pointer`, `block-allocated-status`, `block-unallocated-status`, `block-allocated-empty`, `block-shared-subprogram-instances`.

**Oracle:** Observe each retained state only while the same BLOCK's scope is active, publishing
defined snapshots to the controller before termination. Source-independent literals and
full entry/exit/completion observers are required. The source distinguishes termination
of a BLOCK from RETURN/END of a procedure and from termination of the image.

**Oracle limitation:** An unsaved target can die even when the pointer is saved; reset or re-associate before
any later inquiry if that exception applies. Do not observe a dead target, use
addresses, assume component/default initialization implies SAVE, or claim missing
finalizer output alone establishes these retention effects. Existing saved-block
finalization controls retain 7.5.6.3 ownership.

**Dependencies:** 3.120;8.3;7.5.4.6;7.5.6.3p4;9.7.1.3p4;9.7.3.2p3;15.6.2.4;16.9.13/.20;19.5.2.5(7),(11);19.6.2/.5/.6(23).

### S8.5.16-003: SAVE on a common block in a nonexempt scope requires SAVE in every nonexempt declaring scope

**Source:** 8.5.16 p4, second sentence, including antecedent and all three scope exclusions; J3/24-007, physical PDF132. **Class:** Restriction.

**Definition:** If a common block has SAVE in any scoping unit other than a main program, module or
submodule, it must have SAVE in every scoping unit declaring that block that is not one

SAVE keyword is present. Implicit SAVE solely in an exempt scope does not by itself
satisfy this nonexempt antecedent.

**Diagnostic obligation:** not-required.

**Facets:** `all-nonexempt-scopes-saved`, `missing-other-scope-save`, `implicit-only-exempt-scope-control`, `mixed-exempt-scopes`, `bind-implied-save-candidate`, `bare-save-antecedent`.

**Oracle:** Compare complete cross-scope declarations and actual attribute implications before
proposing a diagnostic. Valid controls preserve matching COMMON layouts and legal
execution if reached. A future negative needs its own policy or independently

arbitrary runtime result or generic link failure is an oracle.

**Oracle limitation:** Bound the proposed contrasts to named nonempty common blocks. Blank common's nonpointer
retention follows its separate 8.10.2.5/19.6.6 rules and is not proof of SAVE or a
license for SAVE // syntax. BIND, initialization rules and scope implication cannot be
ignored when judging whether SAVE is absent. The existing canonical-link schema does not

**Dependencies:** 8.5.16p3/p4;8.5.5p3;8.4p3;8.6.7p4;8.6.14p1/C893;8.10.2.1-.5;14.2.3;19.5.1.4;19.6.6(3);4.2p2.
