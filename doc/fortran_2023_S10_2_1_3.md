## 2. Identity, scope, and interpretation

The canonical identity of the first entry is `F2023:S10.2.1.3-001`.
The edition is implicit within this document. The `S` prefix and local
sequence numbers are assigned by this suite, not by the Fortran standard.

Allocate new numbers without renumbering existing entries. Paragraph numbers
and other source anchors are separate metadata, not the requirement's
identity. A later standard edition needs its own identities and explicit
correspondence mappings. A retired or split entry should retain a record
pointing to its replacement or children.

A requirement describes an observable effect or a program restriction.
Facets distinguish conditions and contexts of that requirement. For example,
the different reasons for reallocating an assignment destination are facets
of one state transition, whereas shape and lower bounds have separate
entries because their oracles differ.

The first runner uses stable file-stem execution IDs such as
`S10_2_1_3_001_valid` and `S10_2_1_3_008_valid__pdt`. A program can contain
several named facets; `S10.2.1.3-001/run/overlap-forward` identifies a
logical fixture below, not a separately executed result or xfail key.
The double-underscore variants are independent executions. Case headers
identify their primary requirement, named facets, and evidence class.
An incidental dependency does not earn coverage.
In section 4, short references such as `-001` mean `S10.2.1.3-001`.

These identities do not prescribe compiler diagnostic identifiers.
A diagnostic catalogue can map a compiler's stable code to the source
paragraph and the corresponding S requirement. The runner recognizes extended IDs and reads case headers and out-of-band
fixture manifests. Generic audits cross-check every registered catalogue,
its independently inventoried source units, and its cases. It does not
infer requirement definitions from compiler behavior.

### 2.1 Common guards

Every definition below inherits these conditions:

* The statement is an eligible intrinsic assignment under 10.2.1.1,
  10.2.1.2, and Table 10.8, not a top-level defined assignment.
* Objects, expressions, targets, and allocation states satisfy the
  applicable requirements elsewhere in the standard. A local permission
  does not waive those requirements.
* Assertions inspect only defined, accessible objects and valid inquiry
  arguments. An undefined value or dangling pointer is not an oracle.
* Processor choices and the as-if permissions in paragraphs 7 and 16 are
  respected. Do not require a particular loop direction, component order,
  temporary, storage address, or allocation implementation.

In particular, allocation effects below do not make every scalar-to-array,
coarray, polymorphic, or parameter-mismatched assignment conforming.
The eligibility check must precede the effect check.

### 2.2 Requirement classes and diagnostic expectations

| Class | Meaning | Evidence model |
| --- | --- | --- |
| Effect | Behavior of a conforming execution | A conforming program with explicit result or state assertions |
| Restriction | A condition the program must satisfy | Conforming controls; isolated violations only in an explicitly classified diagnostic-policy tier |
| Undefined result | The assigned object has no defined value in the specified situation | Retain the requirement and its oracle limitation; do not manufacture a value assertion |

None of the restrictions in this catalogue establishes, by itself, a
mandatory compile-time diagnostic or runtime trap. A future negative case
must record a separate diagnostic obligation and its basis, or identify its
expectation as additional LFortran policy. Do not execute a nonconforming
program and treat an arbitrary outcome as a standard-required failure.

All entries now have source fixtures, but this is not equivalent to full
effect coverage. Restrictions currently have conforming controls rather
than diagnostic-policy violations. The undefined-result entry retains
oracle status `no-portable-direct-oracle`, even when a context case runs.
Ordering permissions are recorded as oracle qualifications rather than as
requirements that a processor exercise every possible order.

## 5. Requirement definitions and test facets

### S10.2.1.3-001: Assignment has snapshot evaluation effects

**Source:** p1, first two sentences; p4. **Class:** Effect.

**Definition:** Assign the appropriately converted expression value with effects equivalent to
evaluating the RHS and the expressions in the LHS designator before any destination
portion is defined. References to the destination within either side are permitted,
subject to -002 and the expression rules.

**Diagnostic obligation:** not-required.

**Facets:** `same-type-value`, `overlap-forward`, `overlap-backward`, `reversal`, `lhs-index-from-old-value`, `substring-overlap`, `self-reallocation`, `enumeration-value`.

**Oracle:** Compare with an independently specified pre-assignment result. Include scalar, section,
and whole-array cases; do not assert evaluation order or that a temporary was physically
created. -014 through -022 and -024 through -032 refine the conversion and derived-type
effects.

### S10.2.1.3-002: The two sides' evaluations are independent

**Source:** p1, last sentence. **Class:** Restriction.

**Definition:** Evaluation of expressions in the LHS designator must not affect, or be affected by,
evaluation of the RHS.

**Diagnostic obligation:** not-required.

**Facets:** `independent-operands`, `lhs-affects-rhs`, `rhs-affects-lhs`.

**Oracle:** Run only the conforming controls in the conformance tier. For a proposed
diagnostic-policy violation, record the interfering state and a minimal repair that
removes the interference. Other expression restrictions may also apply; an arbitrary
execution order is not an oracle for a violating program.

### S10.2.1.3-003: Assignment through a pointer defines its target

**Source:** p2. **Class:** Effect.

**Definition:** With a pointer LHS, intrinsic assignment writes the expression value to its target
rather than performing pointer assignment.

**Diagnostic obligation:** not-required.

**Facets:** `scalar-target`, `array-target`, `strided-target`, `association-preserved`.

**Oracle:** Check target values and the continuing association to the original live target. Use an
associated, definable target satisfying 10.2.1.2; an unassociated pointer is not a valid
control.

### S10.2.1.3-004: An unallocated array cannot acquire shape from a scalar

**Source:** p3, first sentence. **Class:** Restriction.

**Definition:** If the allocatable LHS array is unallocated, the RHS must have the same rank.

**Diagnostic obligation:** not-required.

**Facets:** `unallocated-array-rhs`, `unallocated-scalar-rhs`, `allocated-scalar-control`.

**Oracle:** The positive unallocated case uses a conforming same-rank array RHS. The isolated
scalar-RHS violation is repaired by allocating the LHS first. Do not require a
compile-time error for an allocation state that is only known at runtime, or execute the
violation as a required-failure test.

### S10.2.1.3-005: Assignment deallocates an incompatible existing allocation

**Source:** p3, second sentence. **Class:** Effect.

**Definition:** An allocated allocatable destination is deallocated when an array RHS differs in shape,
corresponding length parameters differ, or, for a polymorphic destination, the dynamic
type or corresponding kind parameters differ.

**Diagnostic obligation:** not-required.

**Facets:** `shape-change`, `length-change`, `dynamic-type-change`, `polymorphic-kind-change`, `unchanged-characteristics`.

**Oracle:** Use eligible assignments that isolate each trigger, then check the characteristics and
values specified by -006 through -011. The no-trigger control checks preservation of
observable destination bounds. Do not test storage-address changes or inspect a pointer
made undefined by deallocation. Lifecycle-sensitive cases also need the finalization
rules.

### S10.2.1.3-006: An unallocated allocatable destination is allocated

**Source:** p3, allocation lead-in following the deallocation conditions. **Class:** Effect.

**Definition:** An eligible allocatable destination that is initially unallocated, or becomes
unallocated during assignment, is allocated before receiving the assigned value.

**Diagnostic obligation:** not-required.

**Facets:** `initially-unallocated-scalar`, `initially-unallocated-array`, `after-deallocation`, `empty-array`.

**Oracle:** Check allocation status and the assigned value separately. An allocated zero-sized array
is not the same state as an unallocated array. Allocation characteristics are covered by
the following entries.

### S10.2.1.3-007: Polymorphic allocation takes the RHS type and kind

**Source:** p3, bullet 1. **Class:** Effect.

**Definition:** Allocation of a polymorphic assignment destination uses the dynamic type and kind
parameters of the RHS.

**Diagnostic obligation:** not-required.

**Facets:** `extension-type`, `unlimited-polymorphic-intrinsic`, `parameterized-derived-kind`, `changed-dynamic-type`.

**Oracle:** Establish the resulting dynamic type, kind parameters, and payload using appropriate
type guards and inquiries. Do not infer the dynamic type from equal payload values
alone. Keep length and shape unchanged when isolating the type/kind facets.

### S10.2.1.3-008: Allocation establishes deferred type parameters

**Source:** p3, bullet 2. **Class:** Effect.

**Definition:** Each deferred type parameter of the allocated destination is established from the
corresponding RHS parameter.

**Diagnostic obligation:** not-required.

**Facets:** `deferred-character-length`, `zero-character-length`, `derived-length-parameters`, `fixed-parameter-control`.

**Oracle:** Check the parameter values as well as the payload. This does not make a nondeferred
parameter changeable. Compare a whole allocatable character assignment with an already
allocated substring assignment to separate allocation from ordinary truncation/padding.

### S10.2.1.3-009: Scalar-RHS reallocation retains previous array bounds

**Source:** p3, bullet 3. **Class:** Effect.

**Definition:** If an existing allocatable array is reallocated for an assignment with a scalar RHS, its
allocation retains the previous bounds.

**Diagnostic obligation:** not-required.

**Facets:** `character-length-change`, `polymorphic-type-change`, `nonunit-lower-bounds`, `zero-extent-control`.

**Oracle:** Start with an allocated array, capture its observable bounds, and trigger an eligible
length or type change with a scalar RHS. Check the bounds, new characteristics, and
scalar expansion. An initially unallocated array with a scalar RHS instead violates
-004.

### S10.2.1.3-010: Array-RHS allocation takes the RHS shape

**Source:** p3, bullet 4, shape provision. **Class:** Effect.

**Definition:** When an allocatable destination is allocated during an array-RHS assignment, the
allocation has the RHS shape.

**Diagnostic obligation:** not-required.

**Facets:** `initial-allocation`, `changed-shape`, `same-size-different-shape`, `zero-extent-dimension`, `section-rhs`.

**Oracle:** Check every extent, not merely total size or rank. Use distinguishable element values to
check subsequent assignment separately under -013. Same-shape assignment to an existing
allocation is a separate control, not evidence of a new allocation.

### S10.2.1.3-011: Array-RHS allocation uses expression lower bounds

**Source:** p3, bullet 4, lower-bound provision. **Class:** Effect.

**Definition:** Each lower bound of the destination allocated for an array RHS is obtained from the
corresponding element of `LBOUND(expr)`.

**Diagnostic obligation:** not-required.

**Facets:** `whole-array-rhs`, `section-rhs`, `expression-rhs`, `zero-extent-dimension`, `existing-allocation-control`.

**Oracle:** Use independently known bounds and the rules of 16.9.119. Do not substitute the bounds
of a source object's declaration for those of an expression. Empty dimensions require
particular care. In a no-trigger control, differently based but same-shaped arrays do
not imply that the existing destination must adopt the RHS bounds.

### S10.2.1.3-012: A scalar RHS expands over the destination shape

**Source:** p5. **Class:** Effect.

**Definition:** An eligible scalar-to-array assignment has the effect of assigning the scalar value to
every element of the destination shape.

**Diagnostic obligation:** not-required.

**Facets:** `rank-one`, `higher-rank`, `array-section`, `empty-destination`, `scalar-from-destination`.

**Oracle:** Check all selected elements and untouched surrounding elements. Combine a scalar derived
from the old destination with -001. Do not interpret expansion as permission to allocate
an initially unallocated array from a scalar.

### S10.2.1.3-013: Array assignment pairs corresponding elements

**Source:** p6; qualified by p7. **Class:** Effect.

**Definition:** Array intrinsic assignment assigns corresponding elements of the destination and RHS,
without prescribing their processing order.

**Diagnostic obligation:** not-required.

**Facets:** `different-lower-bounds`, `rank-two`, `noncontiguous-section`, `reversed-section`, `empty-array`.

**Oracle:** Check position-by-position values with unequal sentinels. Do not pair elements merely
because their subscripts have the same numeric value, or require a particular traversal
order. Snapshot effects remain required when the two sides overlap.

### S10.2.1.3-014: Numeric assignment to integer uses integer conversion

**Source:** p8; Table 10.9, integer row. **Class:** Effect.

**Definition:** Numeric RHS values assigned to an integer destination are converted as by `INT` with the
destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `integer-kind-change`, `positive-fraction`, `negative-fraction`, `complex-rhs`, `array-conversion`.

**Oracle:** Choose representable inputs with independently known integer results. Check both signs
and nonzero imaginary parts. A comparison with an explicit conversion is secondary
evidence, not the sole oracle, since both paths might share the same compiler defect.

### S10.2.1.3-015: Numeric assignment to real uses real conversion

**Source:** p8; Table 10.9, real row. **Class:** Effect.

**Definition:** Numeric RHS values assigned to a real destination are converted as by `REAL` with the
destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `integer-rhs`, `real-kind-change`, `complex-rhs`, `destination-precision`, `array-conversion`.

**Oracle:** Use exact representable values for basic cases, including a complex RHS with a nonzero
imaginary part. Precision-sensitive cases need an oracle justified by the processor's
numeric model and the conversion rules, not an assumed bit layout or unjustified
universal rounding result.

### S10.2.1.3-016: Numeric assignment to complex uses complex conversion

**Source:** p8; Table 10.9, complex row. **Class:** Effect.

**Definition:** Numeric RHS values assigned to a complex destination are converted as by `CMPLX` with
the destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `integer-rhs`, `real-rhs`, `complex-kind-change`, `both-components`, `array-conversion`.

**Oracle:** Check both components and destination precision. In particular, real/integer sources
must not leave an old imaginary component behind. An optional wide-kind case is not
covered if the corresponding complex kind was not exercised.

### S10.2.1.3-017: BOZ assignment uses the destination conversion

**Source:** p9; Table 10.9, integer and real rows. **Class:** Effect.

**Definition:** A BOZ literal assigned to an eligible integer or real destination is converted using the
corresponding Table 10.9 conversion and destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `binary`, `octal`, `hexadecimal`, `integer-destination`, `real-destination`, `destination-kind`.

**Oracle:** Use bit strings valid for the chosen representation and the BOZ rules, with independent
expected values where available. A real bit-pattern fixture needs a documented numeric
profile; arbitrary bit patterns are not portable controls. This entry does not permit a
BOZ assignment to complex, logical, or character.

### S10.2.1.3-018: Logical assignment converts kind while preserving truth

**Source:** p10. **Class:** Effect.

**Definition:** Logical assignment permits differing kinds and converts the RHS logical value to the
destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `true`, `false`, `same-kind`, `different-kind`, `logical-array`.

**Oracle:** Check truth values through logical operations for supported kind pairs. Do not inspect
an assumed integer encoding of true or false. Same-kind cases remain useful controls
where additional kinds are absent.

### S10.2.1.3-019: Character assignment truncates an overlong RHS

**Source:** p11, introduction and item (1). **Class:** Effect.

**Definition:** If the destination character length is shorter, assignment retains the leftmost
characters that fit and discards the excess on the right.

**Diagnostic obligation:** not-required.

**Facets:** `fixed-length`, `substring-destination`, `zero-length-destination`, `character-array`, `equal-length-control`.

**Oracle:** Use a nonrepeating string and check exact destination contents and unaffected
surrounding characters. Separate fixed-length/substring cases from whole deferred-length
allocatables, whose length can instead change under -005 through -008.

### S10.2.1.3-020: Character assignment pads an underlength RHS

**Source:** p11, introduction and item (2). **Class:** Effect.

**Definition:** If the destination character length is longer, assignment extends the RHS on the right
with the applicable blank character.

**Diagnostic obligation:** not-required.

**Facets:** `fixed-length`, `substring-destination`, `empty-rhs`, `character-array`, `nondefault-kind-profile`.

**Oracle:** Pre-fill the destination with nonblanks and check the padding positions explicitly. The
portable baseline uses default character. Nondefault-kind expectations must respect the
character model rather than assuming a universal padding code point. Whole
deferred-length allocation is a separate path.

### S10.2.1.3-021: Character assignment converts character kind

**Source:** p12. **Class:** Effect.

**Definition:** For eligible differing character kinds, each RHS character is converted through its
`IACHAR` value and `ACHAR` of the destination kind.

**Diagnostic obligation:** not-required.

**Facets:** `representable-characters`, `both-directions`, `array-elements`, `conversion-with-length-adjustment`, `replacement-profile`.

**Oracle:** Use supported kinds and known representable characters for portable value checks. A
character not representable in the destination needs a processor-specific expectation,
not a hard-coded replacement such as `?`. Track unavailable-kind and unresolved-profile
facets separately from passing cases.

### S10.2.1.3-022: Integer-to-enum assignment uses enum construction

**Source:** p13. **Class:** Effect.

**Definition:** In an eligible intrinsic assignment from integer to an enum-type destination, conversion
has the effect of that enum type's constructor applied to the RHS.

**Diagnostic obligation:** not-required.

**Facets:** `enumerator-based-integer-expression`, `constructor-control`, `enum-array`, `same-enum-control`.

**Oracle:** Establish the enum value and type using valid expressions under Table 10.8. In
particular, do not use an arbitrary integer RHS that lacks the required enumerator
primary. Do not generalize this rule to the distinct enumeration-type feature.

### S10.2.1.3-023: Cross-image opaque assignment leaves an undefined value

**Source:** p14. **Class:** Undefined result.

**Definition:** Assignment of C_PTR, C_FUNPTR, or TEAM_TYPE leaves the destination undefined when the
destination and RHS are on different images.

**Diagnostic obligation:** not-required.

**Facets:** `c-ptr-component`, `c-funptr-component`, `team-type-component`, `same-image-control`.

**Oracle limitation:** There is no portable direct value assertion for the undefined result. Retain this gap
instead of asserting nullness, a trap, or a particular bit pattern. A conforming
wrapper-component copy can exercise the context without reading the resulting opaque
component; that does not prove that the component was made undefined. Same-image
controls likewise do not cover the cross-image effect.

**Dependencies:** C915 rules out a naive direct coindexed designator. Concrete contexts require careful
wrapper types, valid initial values, and multiple images. Do not read an undefined
component through an inquiry, comparison, or representation-transfer workaround.

### S10.2.1.3-024: Derived-type pointer components use pointer assignment

**Source:** p15, pointer-component branch; qualified by p16. **Class:** Effect.

**Definition:** Corresponding pointer components are assigned using pointer assignment semantics rather
than copying their targets' values.

**Diagnostic obligation:** not-required.

**Facets:** `data-pointer`, `array-pointer`, `procedure-pointer`, `disassociated-source`.

**Oracle:** Check association to a live source target, or disassociation for a defined disassociated
source. For data pointers, mutate the still-live target through one alias and observe
the other. Do not deep-copy the target or inspect a component whose association status
is undefined.

### S10.2.1.3-025: Ordinary components use matching type-bound defined assignment

**Source:** p15, nonpointer nonallocatable defined-assignment branch; qualified by p16. **Class:** Effect.

**Definition:** A nonpointer nonallocatable component uses a consistent type-bound defined assignment
when its type provides one.

**Diagnostic obligation:** not-required.

**Facets:** `scalar-component`, `array-component`, `matching-binding`, `nonmatching-binding-control`.

**Oracle:** Use a binding with an unmistakable controlled value effect. Confirm that the outer
statement remains intrinsic assignment, and that the applicable component binding, not
an unrelated generic assignment, accounts for the result. Do not require a global
component-callback order.

### S10.2.1.3-026: Other ordinary components use intrinsic assignment

**Source:** p15, remaining nonpointer nonallocatable components; qualified by p16. **Class:** Effect.

**Definition:** Other nonpointer nonallocatable components are assigned intrinsically from the
corresponding source components.

**Diagnostic obligation:** not-required.

**Facets:** `intrinsic-component`, `nested-derived-component`, `array-component`, `no-matching-type-bound-assignment`.

**Oracle:** Give components distinguishable values and check recursive assignment effects. A nested
component may in turn require one of the other dispatch rules. A test must not assume
the entire object can always be implemented as a raw representation copy.

### S10.2.1.3-027: Allocated coarray components use intrinsic assignment

**Source:** p15, allocated-coarray-component branch; qualified by p16. **Class:** Effect.

**Definition:** An allocated coarray component is assigned intrinsically from its corresponding source
component.

**Diagnostic obligation:** not-required.

**Facets:** `allocated-scalar-component`, `allocated-array-component`, `per-image-values`.

**Oracle:** Establish conforming allocations, shapes, and parameters first, then check local
assigned values on each image. Follow the coarray allocation and synchronization
requirements. This is not the noncoarray allocatable deallocate-and-copy sequence in
-029 through -032, nor permission to assign to an unallocated coarray.

### S10.2.1.3-028: An unallocated source coarray requires an unallocated destination

**Source:** p15, sentence about unallocated coarray components. **Class:** Restriction.

**Definition:** When the source coarray component is unallocated, the corresponding destination
component must be unallocated.

**Diagnostic obligation:** not-required.

**Facets:** `both-unallocated`, `allocated-destination-unallocated-source`.

**Oracle:** The positive control keeps both components unallocated. The mismatched-state case
belongs only to a separately specified diagnostic-policy tier. Do not interpret the
restriction as an instruction to automatically deallocate an allocated destination
coarray component.

### S10.2.1.3-029: Noncoarray allocatable components discard an old allocation

**Source:** p15, noncoarray allocatable sequence, item (1), with item (2)'s source-allocation condition. **Class:** Effect.

**Definition:** An allocated noncoarray allocatable destination component is deallocated first. If the
source component is unallocated, no subsequent allocation or value assignment occurs,
leaving the destination unallocated.

**Diagnostic obligation:** not-required.
