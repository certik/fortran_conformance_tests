### S7.5.1-001: BIND derived-type storage follows the selected companion processor

**Source:** 7.5.1 p7, last sentence; J3/24-007, 18 December 2023, PDF 88, printed 74, lines 2-3. **Class:** Effect.

**Definition:** For a derived type with BIND, the storage sequence is the one required by the selected
companion processor under 5.5.7 and 18.3.4. Ordinary component declaration order alone
supplies no such default layout guarantee. This is an interoperability obligation, not a
promise of particular byte offsets, padding, alignment, endianness or a numeric kind
identifier. A BIND type and a same-layout Fortran type are not thereby the same derived
type.

**Diagnostic obligation:** not-required.

**Facets:** `companion-member-order`, `companion-selection-evidence`.

**Oracle:** A finite cross-language member-value exchange can observe one declared interoperability
relationship only after the actual companion and matching prototype premises are
independently established. C1801-C1806 constrain the Fortran record; the existing C
array bridge is not evidence for struct member layout. No derived-definition fixture
currently supplies this independent companion/layout qualification.

**Oracle limitation:** Numeric/model/storage-width inquiries do not prove an internal representation, and
successful arithmetic or the needs-oracle real BOZ case cannot supply this layout
premise. No invalid twin or undefined-value trap follows from this effect. The native
SEQUENCE storage obligation is separately owned by S7.5.2.3-001.

**Dependencies:** 5.5.7 p1-p2 (PDF 66); 18.1 p4 and 18.2.2 p3 (PDF 516); 18.3.1, 18.3.4/C1801-C1806/p2-p3
and 18.3.7 p2-p3 (PDF 525-529). The source of component position correspondence is
18.3.4 p2, not Fortran type-identity matching in 7.5.2.4.
