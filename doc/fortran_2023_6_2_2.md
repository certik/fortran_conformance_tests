### R603: A name begins with a letter and has an alphanumeric suffix

**Source:** 6.2.2 R603 (PDF page 68, printed page 54, line 14). **Class:** Syntax.

**Definition:** A name starts with a Fortran letter, followed by zero or more Fortran letters, decimal
digits, or underscores. Digits and underscores are allowed after, but not instead of,
the initial letter. Special characters are not name characters. C601 separately limits
the total length.

**Diagnostic obligation:** required.

**Facets:** `single-letter`, `letter-suffix`, `digit-suffix`, `embedded-underscore`, `consecutive-underscores`, `trailing-underscore`, `initial-letter`, `alphanumeric-suffix`.

**Oracle:** Conforming programs must compile and execute their integer self-checks. The
single-letter cases exercise an empty suffix; the longer spellings exercise every
upper-case and lower-case letter and every decimal digit in suffix positions. Underscore
controls check embedded, consecutive, and trailing occurrences. Isolated declarations
violate either the initial-letter condition or the suffix character class; each has a
minimal conforming repair. Under 4.2 p2(3), these syntax violations require diagnostic
capability, not a particular severity, rule number, or refusal to compile.

**Oracle limitation:** These are free-form name-token cases, not tests of fixed-form blank handling,
continuation, keyword use, or case equivalence. The runner requires LFortran to reject
with a diagnostic at the marker; this is its diagnostic-testing convention, not an
additional R603 obligation. Reference results must distinguish a missing diagnostic from
acceptance with a relevant diagnostic.

**Dependencies:** 4.1.1 p1 defines optional repetition. 6.1.1 p2/R601, 6.1.2 p1-p3, 6.1.3 p1-p3, and
6.1.4/R602 define the character classes (PDF page 67). 4.1.3/R402 applies name syntax to
assumed xyz-name rules. 4.2 p2(3) establishes diagnostic capability; the non-FORMAT
format-specification exception in 4.2 p3 is inapplicable to these declarations.

### C601: A name has at most 63 characters

**Source:** 6.2.2 C601 (PDF page 68, printed page 54, line 15), associated with R603. **Class:** Restriction.

**Definition:** The total length of a name cannot exceed 63 characters. As a constraint on R603, the
limit applies wherever name syntax is used, including the assumed xyz-name forms; it is
not limited to variable declarations.

**Diagnostic obligation:** required.

**Facets:** `length-63`, `distinct-final-character`, `module`, `type`, `component`, `procedure`, `dummy`, `program`, `length-64`.

**Oracle:** Preserve C601_valid and its eight existing facets: the boundary-length names must
compile and execute all existing checks, including separately valued names differing
only in character 63. Preserve the seven C601_invalid execution IDs and their
single-occurrence 64-character names. Each isolated violation must be diagnosed. The
invalid container claims only length-64, which is true of every contained case; its
different entity contexts are not all credited to each case.

**Oracle limitation:** The standard requires diagnostic capability rather than fatal rejection. The existing
reference allowance for the long-names warning is retained, so a relevant portability
diagnostic can corroborate C601 even if compilation succeeds. The runner's stronger
LFortran rejection convention and the existing valid fixture's effect evidence
classification are unchanged.

**Dependencies:** 4.1.2 p2 makes a syntax-associated constraint part of that syntax term at every
occurrence. 4.1.3/R402 defines assumed xyz-name syntax. 4.2 p2(3) requires
detection/reporting capability for numbered constraints. R603 supplies the character
grammar; 5.5.1 p1 and 6.2.2 p1 describe uses of names without adding a separate length
obligation.

## Fixture scope and controls

The finite plan has eight R603 facets and nine C601 facets. All sources
in this packet use free form (`.f90`) and only the listed Fortran character
graphics. No character-code ordering, optional kind, coarray support, or
other optional processor feature is assumed. The cases do not require a
Fortran 2023-only feature, so an explicitly reported Fortran 2018 reference
mode can corroborate these rules.

| `R603_valid__underscores.f90` | 1 | Embedded, consecutive, and trailing underscores |
| `R603_valid__repairs.f90` | 1 | Conforming controls for initial-letter and suffix-character violations |

| `C601_invalid.f90` | 7 | Only the common `length-64` facet, not every context on every case |

There are four valid programs and twelve isolated invalid executions.
New valid R603 programs are positive controls with explicit integer
self-checks; the existing C601 valid program keeps its effect evidence
classification. Every new negative case has one marked malformed name,
is otherwise a complete program, and uses an explicit `! case:` boundary.
The repair program adds a letter before a leading digit or underscore,
substitutes a letter for a leading special character, and substitutes an
underscore for each forbidden suffix character.

The C601 source statements, case boundaries, execution IDs, valid header,
and existing `long-names` reference-warning allowance are preserved.
Adding the catalogue and invalid-container facet changes review
fingerprints; existing reviews are not silently renewed.

## Diagnostic interpretation and boundaries

Both obligations are numbered syntax/constraint requirements with required
diagnostic capability under 4.2 p2(3). A diagnostic need not be fatal or
carry the standard's rule number. The runner's LFortran negative-case
contract is stronger: an unsuccessful compilation and an error spanning
the marked line. Reference outcomes distinguish rejection from an allowed
diagnostic without rejection. Compiler disagreement is observation
evidence, not a reason to alter the language oracle.

The notes create no additional acceptance or rejection rules. Case
equivalence, keyword spellings, fixed-form blank treatment, continued
tokens, and meanings of other kinds of identifier belong to their own
source units and are not claimed as new 6.2.2 obligations here.
