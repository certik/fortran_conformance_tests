### S6.1.2-001: The processor character set includes both letter cases

**Source:** 6.1.2 p3, second sentence (J3/24-007 PDF page 67, printed page 53, lines 17-18), using the p1-p2 letter list. **Class:** Effect.

**Definition:** The processor character set includes the upper-case and lower-case forms of all
twenty-six listed letters. Inclusion of both forms is distinct from their equivalence
outside character contexts. This does not prescribe an ASCII code value or the numerical
relation between a lower-case letter and its upper-case counterpart.

**Diagnostic obligation:** not-required.

**Facets:** `uppercase-letter-repertoire`, `lowercase-letter-repertoire`.

**Oracle:** A default-character value contains the twenty-six upper-case and twenty-six lower-case
letters. Compare every pair of different positions by character equality and require
distinct character values. All positions are within the initialized 52-character value.
This detects collapse of two letters or of the two cases without assuming integer codes,
code ordering, or any particular separation.

**Oracle limitation:** The finite oracle covers representability and distinctness of these 52 source characters
in default character data, using the separately specified default-character and
character-equality semantics. It does not inspect glyph style, processor input encoding,
control characters, optional character kinds, or exhaustive collating-sequence
constraints. No character-code conversion is used, so it does not assume that default
integer can represent the size of the complete processor repertoire, as a default-kind
ICHAR call would require. A successful program is not approval of the fixture.

**Dependencies:** 6.1.2 p1-p2 defines the alphabet (PDF page 67). 7.4.4.2 p2-p3 supplies default character
and the Fortran repertoire (PDF page 84); 7.4.4.3 p2-p4 gives literal kind and
representable characters (PDF page 85). 10.1.5.5.1 p7-p8 defines character equality
without depending on the collating order (PDF pages 180-181). The avoided character-code
result-kind precondition is in 16.9.105 p5 (PDF page 419).

### S6.1.2-002: Letter case is equivalent outside character contexts

**Source:** 6.1.2 p3, third sentence (J3/24-007 PDF page 67, printed page 53, lines 18-19). **Class:** Effect.

**Definition:** In program units, a lower-case letter is equivalent to the corresponding upper-case
letter except within a character context. Under 3.21, character contexts are character
literal constants and character string edit descriptors. The exception is not permission
to fold the values of literals or output edit strings: their defining rules determine
those values. Comment text has no effect under the separate source-form rules; it is not
a third character context with an observable case-preservation effect.

**Diagnostic obligation:** not-required.

**Facets:** `all-letter-name-equivalence`, `mixed-case-keywords-and-calls`, `character-literal-exception`, `character-string-edit-exception`.

**Oracle:** Four independent programs separate the contexts. One declares all twenty-six one-letter
identifiers in upper case, assigns distinct integers through lower-case uses, and reads
them in upper case. Another mixes keyword and program/procedure-name case and checks a
call's scalar result. The literal program uses both delimiter forms, checks
corresponding character positions, and requires each upper/lower pair to differ, so
folding both input and expected literals cannot produce a false pass. The
FORMAT-statement program outputs both delimiter forms to initialized fixed-size internal
records, checks IOSTAT before reading them, and checks exact positions and unequal case
pairs.

**Oracle limitation:** This is a finite plan, not coverage of every keyword, operator, name context, source
form, literal rule, or I/O operation. Character-context checks depend on 7.4.4.3 and
13.9 and are deliberately separate from the no-I/O name and literal cases. Neither a
fixed ASCII case offset nor an ordering between the two cases is assumed. Comments are
not given a fake preservation assertion. No negative program is inferred merely from
this semantic equivalence rule.

**Dependencies:** 3.21 (PDF page 21) defines both character contexts. 6.2.2/R603/C601 owns name grammar
(PDF page 68). 6.3.1 p2 and 6.3.2.3 p1 (PDF pages 71-72) distinguish admissible comment
characters from comments' lack of effect; fixed-form commentary is separately specified
by 6.3.3.2 (PDF page 73). 7.4.4.3 p1-p5 supplies character literals (PDF pages 85-86).
13.3.2/R1322/C1313 and p5-p7 supplies edit-string syntax and its case exception (PDF
page 292); 13.9 p1-p2 supplies output-only character-string editing (PDF page 307).
Native character identity, not ASCII collation, follows from 7.4.4.4 p1 and 16.9.105 p5.
