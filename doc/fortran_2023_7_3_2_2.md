new fatal-rejection policy and no nonfatal reporting allowance by default.

and companion C setup; the shared runner has no per-family include flag.

supported default/double KIND inquiries and character uses its default kind.

missing mappings cause an explicit support failure, never an unsupported
declaration kind or a silent fallback. C type codes are matched using
ISO_C_BINDING kind-equality flags, not a native bit layout or an assumed
unique code for each Fortran kind. Character sizes are qualified to C_CHAR.
The shared suite has no optional profile for those mappings; reusable
profile/header integration is pending with the parent, not hidden as a
passing portable configuration.

Pending source/use evidence is explicit for declaration ordering, later

### C714: Assumed-type entities are eligible dummy data objects

**Source:** 7.3.2.2 C714, PDF 78, printed 64, lines 25-26. **Class:** Restriction.

**Definition:** An assumed-type entity must be a dummy data object, not an ordinary local or a dummy
procedure. It cannot have ALLOCATABLE, CODIMENSION, INTENT(OUT), POINTER or VALUE and
cannot be an explicit-shape array. Scalar, assumed-shape, assumed-size and assumed-rank
dummy data objects are not excluded by this constraint. Other attributes and uses remain
subject to their own rules.

**Diagnostic obligation:** required.

**Facets:** `nondummy-excluded`, `dummy-procedure-excluded`, `allocatable-excluded`, `codimension-excluded`, `intent-out-excluded`, `pointer-excluded`, `value-excluded`, `explicit-shape-excluded`, `scalar-dummy`, `assumed-shape-dummy`, `assumed-size-dummy`, `assumed-rank-dummy`.

**Oracle:** Eight compile-only invalid/control pairs change only the offending dummy-list entry,
EXTERNAL or prohibited attribute, or explicit upper bound. The codimension case is a
scalar nonallocatable dummy with legal explicit coshape and requests coarray mode. Four
independent runtime admission controls use allowed scalar and array forms and return
checked inquiry sentinels without reading assumed-type payloads.

**Oracle limitation:** The repairs deliberately remain compile-only controls, not claimed runtime effects. No
caller introduces an allocatable/pointer/rank mismatch into an invalid declaration. The
six attribute/shape negatives declare lines 1-3 as a single-entity specification span:
the SUBROUTINE dummy binding and its explicit attribute/shape declaration are both
endpoints of that entity's restriction. The END statement at line 4 is excluded, so a
whole-procedure recovery range does not fit. Nondummy and procedure negatives retain
exact declaration points. Every accepted report also needs a causal
eligibility/attribute/shape message; same-line unsupported-feature text cannot
substitute. Paired control and source-message review remain necessary even when the
automated gate matches. Coarray implementation failures are failures, not
optional-profile skips. Reporting capability under 4.2 is not mandatory fatal rejection.

**Dependencies:** 4.1.2 p3 and 4.2 p2(3), PDF 45-46; 8.2/R801 (PDF 117), 8.5.6/C826/C828 (PDF 121-122),
8.5.8.2-.7 (PDF 125-129), and 15.4.2.2 (PDF 325). C715 separately limits every use of
the admitted dummy.

### C715: Assumed-type names have a bounded set of permitted uses

**Source:** 7.3.2.2 C715, PDF 78, printed 64, lines 27-30. **Class:** Restriction.

**Definition:** An assumed-type variable name cannot occur in a designator or expression except as an
actual argument for an assumed-type dummy, or as the first argument of IS_CONTIGUOUS,
LBOUND, PRESENT, RANK, SHAPE, SIZE, UBOUND or ISO_C_BINDING's C_LOC. Being unlimited
polymorphic does not add CLASS(*) operations to TYPE(*). The exceptions do not waive the
named procedure's argument, state, rank, OPTIONAL, TARGET, contiguity or size
requirements.

**Diagnostic obligation:** required.

**Facets:** `assumed-type-forwarding`, `is-contiguous-first`, `lbound-first`, `present-first`, `rank-first`, `shape-first`, `size-first`, `ubound-first`, `c-loc-first`, `designator-excluded`, `unlisted-intrinsic-excluded`, `class-receiver-excluded`, `later-argument-source-use`.

**Oracle:** Six independently compiled controls exercise forwarding, contiguity, bounds/shape/size,
optional presence, rank and C_LOC. Three compile-report pairs isolate an assumed-type
array-element designator passed to a scalar TYPE(*) receiver, an unlisted STORAGE_SIZE
inquiry, and forwarding to CLASS(*) rather than TYPE(*). Repairs change the designator's
source declaration to INTEGER, the inquiry to RANK, or the receiver keyword to TYPE.
Each diagnostic is located on the single offending statement and must describe the
prohibited assumed-type use.

**Oracle limitation:** The designator pair has a scalar receiver, so neither C716 nor an array-rank mismatch is
introduced. STORAGE_SIZE admits a data object of any type; KIND would add an independent
intrinsic-type premise. CLASS(*) is type compatible with all entities, so its forbidden
receipt of TYPE(*) is not a concrete-type mismatch. PRESENT is applied only to an
OPTIONAL dummy; no other inquiry uses an absent argument. Bounds and sizes use
initialized nonzero arrays, and the contiguity control specifies CONTIGUOUS rather than
demanding a processor-dependent section layout. C_LOC uses a live scalar TARGET of C_INT
kind and compares C pointers with C_ASSOCIATED, never as integers. Generic type
mismatch, recovery ranges and unsupported syntax are not substitute evidence.

**Dependencies:** 4.2 p2(3), PDF 46; C714/C716 and 7.3.3; 8.5.7 (PDF 123-124); 15.5.2.4-.5 (PDF 339-340);
16.9.115/119/163/171/185/194/200/215 (PDF 424-425,445,449,456,459,462,469); 18.2.3.2 and
18.2.3.7 (PDF 518,523). Canonical intrinsic semantics and C ABI coverage are
dependencies, not newly owned requirements.

### C716: Assumed-type forwarding to assumed-rank preserves descriptor eligibility

**Source:** 7.3.2.2 C716, PDF 78, printed 64, lines 31-32. **Class:** Restriction.

**Definition:** When an assumed-type actual corresponds to an assumed-rank dummy, the actual must itself
be assumed-shape or assumed-rank. An ordinary scalar assumed-type dummy and an
assumed-size assumed-type dummy do not meet this condition. An assumed-rank actual may
have scalar effective rank; a concrete-type scalar actual is outside the assumed-type
premise.

**Diagnostic obligation:** required.

**Facets:** `assumed-shape-forwarding`, `assumed-rank-scalar`, `assumed-rank-array`, `scalar-assumed-type-excluded`, `assumed-size-excluded`, `typed-scalar-outside-premise`.

**Oracle:** Two compile-report pairs forward scalar or assumed-size TYPE(*) to an explicitly
interfaced TYPE(*) assumed-rank receiver. Repairs change only the forwarding dummy's
shape form to assumed-rank or assumed-shape. Three runtime controls check assumed-shape
forwarding, assumed-rank forwarding with scalar and array effective arguments, and a
concrete INTEGER scalar outside the premise.

**Oracle limitation:** The invalid assumed-size form is legal under C714; an explicit-shape TYPE(*) negative
would not isolate C716. The receiving assumed-rank accepts either actual rank, so the
repaired shape change does not cure a second ordinary rank mismatch. All calls are to
assumed-type receivers, satisfying C715. Exact call-point and causal reporting gates
apply; a whole-procedure recovery range cannot satisfy the point. Runtime sentinels
start negative and do not inspect unknown payloads.

**Dependencies:** 4.1.2/4.2 (PDF 45-46); 8.5.8.3/.5/.7 (PDF 125-129); 15.4.2.2 and 15.5.2.4-.5 (PDF
325,339-341); 16.9.171 (PDF 449).

### S7.3.2.2-001: TYPE declarations require an available previously defined named type

**Source:** 7.3.2.2 p2, PDF 78, printed 64, lines 15-18. **Class:** Restriction.

**Definition:** In a type declaration statement, a derived, enum or enumeration specifier within TYPE
must name a previously defined type. For a function result, specifying the type in the
FUNCTION statement is also permitted when the definition is inside the function or the
type is available there through use or host association. The function exception does not
permit arbitrary forward declarations of other objects.

**Diagnostic obligation:** context-dependent.

**Facets:** `previous-derived`, `previous-enum`, `previous-enumeration`, `function-prefix-host`, `function-prefix-use`, `ordering-source-use`.

**Oracle:** Four runtime positive controls use a prior derived type and host-associated function
prefix, a USE-only prefix whose caller imports the type under a different name, a
previously defined named enum, and a previously defined enumeration type. Small
returned/component/ordinal values are checked.

**Oracle limitation:** The two F2023 nonderived controls retain their actual value oracles if a compiler lacks
the syntax. They are not replaced by integer or unnamed-ENUM controls. Function-result
interpretation for body-local definitions is separately exercised by S7.3.2.2-002.
Coverage is not automatically credited to defining 7.5/7.6 constraints.

**Dependencies:** 7.1.2, 7.3.2.1/R703, 7.5.2.4 (PDF 90), 7.6.1/C7112 and 7.6.2/C7116 (PDF 109-112), 8.2
(PDF 117), 15.6.2.2 p3-p4 (PDF 354), and the canonical USE/host-association rules in
19.5.1. 4.1.2 p3 distinguishes prose restrictions from numbered reporting obligations.

### S7.3.2.2-002: A function-prefix TYPE result follows its body-local type definition

**Source:** 7.3.2.2 p2, PDF 78, printed 64, lines 16-20. **Class:** Effect.

**Definition:** When a function result's TYPE specifier is in the FUNCTION statement and names a type
defined in that function body, the result is interpreted as declared with that type
immediately after the definition. The result's other attributes still need their
ordinary specification; the type and parameters must not be redundantly specified both
in the prefix and a result declaration.

**Diagnostic obligation:** not-required.

**Facets:** `body-local-derived-result`, `body-local-enum-result`, `body-local-enumeration-result`.

**Oracle:** Three independent functions define their result type inside the body and return
initialized values. The nonpolymorphic derived result is expanded by formatted internal
I/O to its single public INTEGER component; SS,I0 plus checked IOSTAT and an initialized
record gives an exact decimal result. Named enum and enumeration results are converted
by INT and compared to their expected integer/ordinal values.

**Oracle limitation:** The body-defined types are not silently moved into a host module to satisfy a compiler.
No local type has private, pointer, allocatable or type-bound components. The controls
do not assert processor storage layout or read an uninitialized result. Unsupported
F2023 results retain runtime expectations.

**Dependencies:** 15.6.2.2 p3-p4 (PDF 354); 7.6.1-.2 (PDF 109-112); 12.6.3 p4-p8 and 12.6.4.1 (PDF
263-264); 13.7.2.1-.2 (PDF 295-296); 16.9.110 p3/p5(iv)-(v), INT (PDF 421-422). Runtime
interpretation, not blanket error reporting, follows 4.2 p2(1).

### S7.3.2.2-003: Assumed-type dynamic type and parameters come from the effective argument

**Source:** 7.3.2.2 p3, PDF 78, printed 64, lines 23-24. **Class:** Effect.

**Definition:** An assumed-type entity takes its dynamic type and type parameter values from its
effective argument. It still has no declared type. Effective argument is the
argument-associated entity, not necessarily the spelling of the ultimate actual. The
separate restrictions on derived actuals with parameters, type-bound procedures or final
subroutines continue to apply.

**Diagnostic obligation:** not-required.

**Facets:** `descriptor-integer-kind`, `descriptor-real-kinds`, `descriptor-character-length`, `assumed-derived-identity-source-use`.

**Oracle:** A real mixed-language runtime fixture forwards an assumed-rank TYPE(*) dummy to an
assumed-type BIND(C) receiver. The initialized actuals use the mandatory C_INT kind,
supported default/double REAL kind inquiries and default CHARACTER at two lengths. The
checker validates scalar rank, nonnull base address, CFI_VERSION, a type code mapped to
the actual Fortran category/kind, and elem_len. Fortran derives an eligibility flag for
every integer or real macro counterpart in Table 18.4 by comparing supported
ISO_C_BINDING kind values. Distinct C type codes for the same Fortran kind are accepted
only through that source-supported mapping, not merely because storage sizes match.
Default CHARACTER must map to C_CHAR; its two expected lengths are 3 and 5 bytes. All
status sentinels are initialized. No dimension or payload is dereferenced and no private
descriptor layout is reproduced.

**Oracle limitation:** The selected Fortran processor's matching ISO_Fortran_binding.h and ABI-compatible
companion C configuration are required. The C build step explicitly requests that
processor header; only its bytes are staged, with path/hash and companion identity
recorded and snapshot-checked. A separate standard-property profile qualifies the
optional default/double-real and default-character C mappings before the fixture
executes; failure of mandatory C_INT is an error, not an optional skip. Optional
negative C kind constants are never used as declaration kinds. The in-fixture mapping
guard remains an explicit consistency check, not a fallback to another kind or an empty
control. C codes are not assumed unique for a Fortran kind: category-separated alias
flags preserve the Table 18.4 relation rather than inferring identity from sizeof.
Header/version mismatch is an interface failure before local type/parameter propagation
is observed. A successful run still needs independent interface qualification; no
arbitrary derived-type identity or general compatibility is inferred.

**Dependencies:** C714-C716; 15.5.2.4 p6 and 15.5.2.5 p2 (PDF 339-340); 18.2.2 p2-p6, including negative
unsupported-kind constants (PDF 516-517); 18.3.7 p2(5) (PDF 529), 18.4/18.5.1 (PDF 531),
18.5.2-.4, Table 18.4 and NOTE 2 (PDF 531-535). No owned coverage is claimed for those
canonical interoperability requirements.
